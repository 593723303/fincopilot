# 开发经验记录

这份文档记录 M0–M5 开发过程中遇到的真实问题、诊断过程与最终结论。

与 `benchmarks.md`（记录指标）和 `open-issues.md`（记录待办）不同，
这里记录的是**判断过程**：怎么发现问题、怎么定位、哪些判断是错的、
为什么错。代码可以重写，这些判断过程不能。

每条按「现象 → 定位 → 根因 → 教训」组织。

---

## 一、最危险的一类：静默失效

这类问题的共同特征是**不报错**。系统照常运行、日志干净、指标正常，
只是结果悄悄是错的。它们比崩溃危险得多——崩溃会立刻暴露，静默失效可以潜伏很久。

### 1.1 实验配置没有流转，三组消融全部作废

**现象**：三组消融实验（重排、放宽截断、换模型）的指标几乎一模一样。

**当时的判断（错的）**：这些优化都没用。差点据此收手。

**定位**：换模型后成本应该降到四分之一，实测却几乎没变——这不合理，顺着查下去：

```python
# run.py
exp = load_experiment(args.exp)     # 读了 --exp 指定的配置
# 节点内部
exp = load_experiment()             # 无参数，读的是环境变量 EXP_ID
```

**根因**：`--exp` 只影响评估记录，不影响实际运行。三组实验跑的全是同一个基线配置。

**后果**：如果没查，会错过后面 **+21.3 个百分点**的改进，并得出「重排和放宽截断都没用」的错误结论。

**教训**：
- **配置必须随请求流转，不能走全局状态**。全局配置在单实验时毫无问题，
  一旦要做横向对比就会静默失效——它不报错，只是让所有实验变成同一个。
- **当多组实验结果高度一致时，先怀疑实验本身没生效**，而不是急着下结论。

### 1.2 下载"成功"但内容完全无关

**现象**：下载了两家公司的年报，文件名正确、大小正常。

**定位**：解析统计完全相同（307 页、362 个表格、相同字号分布）——不可能是巧合。
比对 SHA256，两个文件完全相同；读首页，内容既不是茅台也不是宁德，而是第三家公司。

**根因**：巨潮查询接口的 `stock` 参数必须是 `"{code},{orgId}"` 格式。只传 code 不会报错，
会被静默忽略，接口返回全市场最新公告。

**教训**：
- **下载成功 ≠ 下载正确**。凡是从外部获取数据，都要校验内容而非只看状态码。
- 修复时加了强制校验：读 PDF 首页，确认包含目标公司代码，否则删除文件并报错。

### 1.3 成本统计悄悄归零

**现象**：修完流式输出后，成本统计里 `light` profile 变成 `0.0`。

**定位**：单独调用节点能拿到用量，放进图里就是 0。差异只有 config。

**根因**：在 `astream_events` 环境下，LangChain 会把 `ainvoke` 也转成流式执行
（为了产生 token 事件），而**流式响应默认不回传 token 用量**，需要显式 `stream_usage=True`。

**教训**：
- 这不是个别节点的问题，是所有 LLM 调用的共性，**应该在 Provider 层统一解决**，
  逐处添加迟早会漏。
- 成本统计出现「恰好是 0」的值时要警惕——真实用量极少正好为零。

### 1.4 用量累加变成覆盖

**现象**：同一个模型被调用两次，账面上只有后一次的花费。

**根因**：
```python
"by_profile": {**prev.get("by_profile", {}), **cur.get("by_profile", {})}
```
字典展开对同名 key 是**覆盖**而非累加。而且 `query.py` 和 `rag.py` 各写了一套合并逻辑。

**教训**：聚合逻辑只应有一处实现。两处相似的实现，迟早会有一处是错的。

## 二、指标会说谎

这一类问题更隐蔽：**指标本身就是错的**，而人会倾向于相信数字。

### 2.1 覆盖率 100%，其中一部分是错的

**现象**：表格量纲标注覆盖率做到了 100%，看起来完美。

**定位**：抽查了几条，发现：
- 「备查文件目录」这种纯文字表被标成「单位：元」
- 董监高持股表标成「单位：元」，而表格第一行白纸黑字写着「单位：股」

**根因**：兜底逻辑无条件给所有表格套上文档主导量纲，包括非数值表；
且只看表格上方，没有提取表格内部的单位声明。

**结果**：修复后覆盖率**从 100% 降到 79–88%**，但正确性大幅提升。

**教训**：**指标下降反而是进步**。100% 的覆盖率是把错误答案也算进去的结果。
不要只看聚合数字，要抽查具体样本。

### 2.2 文档级召回 93.9%，页码级召回只有 38.8%

**现象**：`Recall@K` 高达 93.9%，但大量问题答不出来。

**根因**：召回是以 **doc_key** 为粒度算的——茅台年报里任何一个块命中都算 100%。
它无法区分「检索到 p6 主要会计数据」和「检索到 p150 无关附注」，
**而后者正是当时的主要失败模式**。

改成页码粒度后，真实召回是 **38.8%**。

**教训**：**指标的粒度决定它能发现什么问题**。粒度过粗的指标不是不精确，
而是会主动掩盖问题，让人以为一切正常。

### 2.3 评估器自己有缺陷，误答率虚高到 50%

**现象**：误答率 50%，看起来系统严重违反拒答约束。

**定位**：看实际回答，那两条「误答」其实都是正确拒答：

```
"我无法提供投资建议。作为财报分析助手，我可以帮助您解读财务报表..."
"我无法提供腾讯控股2025年的营业收入预测，因为...未在已收录的年报中出现"
```

**根因**：拒答识别的关键词表只收了「未找到」类说法，漏了「我无法提供」。

**第二次踩坑**：补全词表后改为全文匹配，又把两道正确题判成了拒答——

```
"贵州茅台的股票代码是600519。 我可以帮助您分析财报数据，但无法提供实时行情..."
                                                      ↑ 被这句误伤
```

**最终解法**：只匹配**第一句**。真正的拒答第一句就表态，免责声明在末尾。

**教训**：
- **评估器自身也需要被测试**。评估集和判定规则错了，所有指标都是假的，
  而且错得很隐蔽——数字看起来完全正常。
- 修改判定规则后**必须回跑历史用例确认没有反转**。

### 2.4 标注过严，让好结果显得很差

**现象**：页码召回为 0 的题，很多 `is_correct = true`（答对了）。

**根因**：同一个数据在年报多处出现（p6 主要会计数据、p9 主营业务分析），
标注只写了 p6，但模型从 p9 答对同样是对的。

**教训**：中间指标受标注方式影响极大。**主指标必须是端到端正确率**——
中间指标再漂亮或再难看，都可能是标注造成的假象。

## 三、语义错位：字段名对，含义不对

### 3.1 report_year 是文档的年度，不是数据的年度

**现象**：问「2024年营业收入」返回空，拒答。

**根因**：一份 2025 年报含 2023–2025 三年数据，但它的 `report_year` 只有 2025。
按 `report_year == 2024` 过滤必然为空。约四分之一题目因此被误拒。

**排查时的陷阱**：因为**检索阶段就返回空，相关度阈值根本没被触及**，
我先花了一轮去调阈值，结果「误拒」反而从 14 条变成 15 条——完全是错误方向。

**教训**：字段名相同不代表语义相同。做过滤前先问一句：
**这个字段描述的是文档的属性，还是内容的属性？**

### 3.2 标题与内容错配

**现象**：某个块 `heading_path = 十、非经常性损益`，而内容是「九、分季度财务数据」。

**根因**：解析循环先遍历整页所有文本行更新标题追踪器，再处理表格，
**表格拿到的是整页最后一个标题**。

**解法**：按页面纵向位置把文本段与表格混合排序，顺序处理。错配降为 0，
且标题路径从一级变完整三级。

**教训**：处理有版面的文档时，**元素的空间顺序即语义顺序**，不能按类型分批处理。

## 四、调试方法

比具体问题更可复用的是方法。

### 4.1 先探查，再设计

写 PDF 解析器之前先写了探查脚本，结果**推翻了三个假设**：

| 原假设 | 真实数据 |
|---|---|
| 表格是需要特殊处理的少数情况 | 75–85% 的页面含表格 |
| 量纲在文档内混用 | 跨公司系统性差异（茅台全用元，宁德全用千元） |
| 单位声明就在表格上方 | 只有 52–64% 如此 |

如果凭假设直接写，三条都会写错。**凭想象写解析器是这类任务最容易返工的地方。**

### 4.2 隔离变量，单独测量

定位截断问题时，没有去跑完整评估（慢且贵），而是写了只测召回的脚本
（不调用生成模型，成本接近零）：

```
检索 top_k=5    63.3%
检索 top_k=20   95.9%
检索 top_k=50   98.0%
```

一下就看出检索本身没问题。

### 4.3 分阶段测量，定位损失发生在哪一步

```
检索 top20   95.9%
截断 top5    44.9%   ← 一步损失 51 个百分点
父块还原     44.9%   ← 无额外损失
```

**信息不是没检索到，是检索到之后被丢掉了。** 这一步测量直接定位了真正的瓶颈。

### 4.4 静态检查要用 AST，不要用字符串匹配

给「禁止节点调用无参 `load_experiment()`」写防回归测试时，第一版用字符串匹配，
结果把 `state.py` **文档字符串里**的说明性提及也报成了违规——
而那段文字恰恰是在解释为什么不能这么调用。

改用 `ast.parse` 查找真实的函数调用节点后才准确。

**教训**：注释和文档字符串里出现函数名是常态，尤其是在解释该函数用法的地方。
静态检查必须基于语法树。

### 4.5 不信任何未经验证的数字

这个项目里被证伪的"显然正确"的判断：

| 判断 | 实际 |
|---|---|
| 量纲覆盖率 100%，做得很好 | 其中一部分标错了 |
| 文档召回 93.9%，检索没问题 | 页码召回只有 38.8% |
| 误答率 50%，拒答约束失效 | 评估器识别不全，实际是 0% |
| 三个实验指标一样，优化没用 | 配置没生效，三个跑的是同一个 |
| 成本估算 ¥0.03 | 实测 ¥0.003，差一个数量级 |
| 重排能解决排序问题 | 各截断深度下均无帮助，部分更差 |
| 标题分块优于定长分块 | 无显著差异，定长反而略高 |
| 强模型质量更好 | 与便宜模型无显著差异，成本差 4.8 倍 |

**共同点：每一个都是「看起来合理的数字」或「看起来合理的假设」。**

后三条尤其值得注意——它们不是算错了，而是**沿用了通用最佳实践却没在
自己的数据上验证**。重排、语义分块、强模型都是 RAG 的标配建议，
在这个场景里全部落空。

## 五、优化达标的完整过程

目标：提升答案正确率。起点 65.6%，终点 86.9%（+21.3 点，置信区间不重叠）。

过程**经历了三次方向反转**：

### 第一次：以为是相关度阈值

观察到大量「不应拒答却拒答了」，算了一下 RRF 分值范围：

```
两路都排第一  2/61 = 0.0328
仅一路命中    1/61 = 0.0164   ← 低于阈值 0.02，直接被拒
```

阈值确实错了，改成 0.010。**结果误拒反而从 14 条变成 15 条。**

教训：阈值错是真的，但不是主因。**修了一个真实的 bug 不代表修了关键的 bug。**

### 第二次：以为是排序

诊断发现检索系统性偏向财务报表附注（p60–120）而非摘要表（p6–7）——
附注里科目名出现频率高，摘要表的 BM25 分数被稀释。看起来是典型的排序问题。

接入重排。**正确率一点没动。**

隔离测量后发现，重排在所有截断深度下都没帮助，top_n=10 时甚至低 9 个百分点。
gte-rerank 是通用语义模型，对中文财报表格的结构化内容判断不如 RRF 融合——
它的分数分布也印证这点（实测集中在 0.11–0.16，区分度极低）。

教训：**负面结果也是结果**，而且要有数据支撑才站得住。

### 第三次：真相是截断深度

分阶段测量定位到 `top_n=5` 的截断一步丢掉 51 个百分点。
放宽到 15 并同步扩大上下文预算后：

| 指标 | 改前 | 改后 |
|---|---|---|
| 正确率 | 65.6% [54.1, 77.0] | **86.9% [78.7, 95.1]** |
| 页码召回 | 38.8% | **88.8%** |
| 表格数值题 | 53.3% | **93.3%** |

置信区间不重叠，是整个项目第一个可以正式声称的提升。

### 最终的消融结论：三个"标配优化"全部无效

四个因子各自的边际贡献：

| 因子 | 效果 | 结论 |
|---|---|---|
| 截断深度 top_n 5→15 | **+21.3 点**，区间不重叠 | 唯一显著因子 |
| 生成模型 plus→flash | -1.7 点，成本降至 1/4.8 | 质量持平，显著省钱 |
| 分块策略 heading→fixed | +1.6 点，区间重叠 | 无显著影响 |
| 重排 关→开 | -1.7 点，成本 +6% | 无效 |

**重排、语义分块、强模型——这三个被广泛推荐的 RAG 优化手段，在本场景
全部没有显著收益。真正起作用的是一个很少被讨论的参数：送进上下文的块数。**

分块策略那条还推翻了架构文档自己的假设（ADR-005 假定标题分块更优）。
事后看原因很清楚：75–85% 的页面含表格，而表格是整块处理的，
根本不经过文本分块逻辑。**最该优化的地方，往往不在通用最佳实践的清单上，
而在你这个场景的数据特征里。**

处理方式是把 heading 策略的保留理由从「检索更准」改成
「产出的 heading_path 对引用展示与排查有价值」——
一个诚实的降级，而不是继续用一个站不住的理由。

### 顺带的成本优化

把生成模型换成 qwen-flash：质量无显著差异（85.2% vs 86.9%，区间大幅重叠），
误答率反而更低，**单题成本从 ¥0.0062 降到 ¥0.0013**。

原因：本场景输入远大于输出（约 4000 入 / 100 出），
而 flash 的输入单价只有 plus 的五分之一。**先看清成本结构，再决定省哪一头。**

## 七、M5：检索里该放什么、不该放什么

M5 本来是做 Agent（多跳推理从 62.5% 升到 100%，n=8），
但这一轮最有价值的三条经验都与 Agent 无关，而与**检索查询该由什么构成**有关。

### 7.1 已经做了标量过滤的字段，不要再进检索文本

**现象**：问「贵州茅台2023年营业收入」，系统答「所提供资料中未找到」。
而答案明明白白印在 p6 的「近三年主要会计数据」表里。

**定位**：换几种查询直接测检索，一次就看清了（`years` 过滤相同，只换文本）：

```
「贵州茅台2023年营业收入是多少？」 → p6 不在前 20
「2023年营业收入」                 → p6 排第 1
「贵州茅台 2023年 营业收入」        → p6 排第 15
```

**根因**：公司名已经由 `company_code` 标量过滤处理过了。
过滤之后候选集里**每一页都写着「贵州茅台」**，这个词在文档内的区分度为零，
却实打实占着 BM25 的词频权重，把真正有区分度的词（年份、科目名）挤了下去。
「是多少」同理。

**教训**：**过滤条件与检索文本要各管各的，不要重复。**
已经能用结构化字段精确限定的，就不要再交给全文检索去「软匹配」一遍——
那不是双保险，是噪声。

### 7.2 反过来：检索需要的字段，必须进文本

同一轮里还有个对称的问题。Agent 的检索工具把 `year` 只当过滤条件用：

```python
retrieve(query, QueryFilters(company_codes=[code], years=[year]))
```

但这里的 `years` 过滤的是 **report_year（文档的报告年度）**，
而一份 2025 年报同时匹配 2023/2024/2025 三个查询年份——**过滤等于没过滤**。
于是问 2023 年和问 2025 年返回的是同一批块，模型把「上期发生额」当成了 2023 年。

而年份这个信息恰恰明写在表格的列头里：`| 主要会计数据 | 2025年 | 2024年 | 2023年 |`。
把年份拼进检索文本（`f"{year}年{query}"`）之后，这道题就对了。

**两条合起来是同一个判断：看这个字段在候选集内部有没有区分度。**
年份有（不同列不同年），公司名没有（整篇都是同一家）。

### 7.3 「合并 / 母公司」是中文财报的第二个量纲问题

**现象**：经营活动现金流量净额同比，算出 -11.43%，标准答案 -33.46%。

**定位**：不猜，直接打印两个候选块的原文：

```
p64 块：第八节财务报告 > 二、财务报表 / 【单位：元】 / | 项目 | 附注 | 2025年度 | 2024年度 |
p66 块：第八节财务报告 > 二、财务报表 / 【单位：元】 / | 项目 | 附注 | 2025年度 | 2024年度 |
```

**逐字相同。** 一张是合并现金流量表（615 亿），一张是母公司现金流量表（326 亿），
而「合并」「母公司」这两个词在解析产物里一个字都没有。

**根因**：报表标题只印在**起始页**，三大报表每张横跨两三页，续页没有任何标题。
解析器按页处理，续页自然拿不到标题。

**修法与单位完全一致——跨页继承，章节一变即失效**（否则「合并」会被带进财务附注）。
这是个值得记住的对应关系：

| 问题 | 表现 | 解法 |
|---|---|---|
| 元 / 千元 / 万元 | 数量级差 1000 倍 | 多级回退 + 跨页继承 |
| 合并 / 母公司 | 同一科目差一倍 | 标题识别 + 跨页继承 |

**教训**：**口径标签必须落到块的正文里，不能只存在元数据或页面布局中。**
检索返回的是文本，模型看不到元数据；而靠「它在第几页」去推断口径，
等于要求模型记住每份年报的排版。

### 7.4 枚举式规则会一直漏，漏到第三次就该换形式

拒答识别的词表已经补过三轮：

1. 首版只收「未找到」类 → 漏掉「我无法提供」，误答率虚高到 50%
2. 补完之后 → 漏掉「我目前没有…数据，因为年报尚未发布」
3. 再补 → 漏掉「年报中未披露第五季度的数据」

每漏一次，就有一次**正确的拒答被记成误答**，拒答能力的改进在指标上完全看不见。

第三次之后换了形式：不再枚举说法，改成匹配构词骨架——

```python
REFUSAL_PATTERN = re.compile(
    r"(未|没有|无法|不能|不予|查不到|找不到)\s*"
    r"(披露|提供|找到|检索到|查到|给出|回答|收录|包含|提及|公布|列示|存在)"
)
```

说法千变万化，骨架只有「否定词 + 动词」这一种。

**教训**：**同一类规则补到第三次还在漏，说明枚举的粒度选错了。**
该退一步找这些个例共同的结构，而不是继续加词。

### 7.5 ReAct 循环的终止条件不能只看 tool_calls 是否为空

run 0025 返回给用户的「答案」原文：

```
calculate
{"expression": "82320067101.68 - 82293107655.25"}
</tool_call>
```

模型把工具调用写成了正文，结构化的 `tool_calls` 字段是空的。
循环里「没有 tool_calls」被当成了「已经给出最终回答」，于是这段原文直接返给了用户。

现在额外检查正文里有没有工具调用的痕迹，有就按一次工具失败计数并要求重发，
由护栏负责收敛——而不是加一个无限重试。

**教训**：**凡是依赖模型「按格式输出」的分支判断，都要准备好格式没守住的那条路。**
小模型尤其如此；而便宜的小模型正是成本优化的方向，这条路绕不开。

### 7.6 修失败用例时，先确认题目本身是对的

这一轮有两道题是**问法与标注自相矛盾**，模型答对反而被判错：

| 原问法 | 标注要的 | 为什么模型没错 |
|---|---|---|
| 「销售净利率是多少」 | 归母净利润 / 营业收入 | 销售净利率的通行口径含少数股东损益 |
| 「财务报表使用的货币单位」 | 千元 | 「货币单位」也可以理解成币种 |

两道都改了问法，**没有改标准答案**。

**教训**：**迁就模型的输出去改标准答案，等于把评估集变成橡皮尺。**
该改的是问法——让题目只有一种读法。

### 7.7 归一化既然能修一个问题，就能毁掉另一个

安全计算器上连踩两次，都是「为了处理 A 而破坏了 B」：

| 改动意图 | 破坏了什么 |
|---|---|
| 剥掉千分位逗号 `replace(",", "")` | `round(x, 2)` 变成 `round(x 2)`，语法错误 |
| 常量统一转 `float` | `round(x, 2)` 的位数变成 `2.0`，`ndigits` 只接受整数 |

修法分别是用前后断言限定逗号（`(?<=\d)[,，](?=\d)`）、以及保留 `int` 原类型。

**教训**：**任何「统一格式」的操作都要先问一句：这个字符在别的位置是不是另有含义。**
逗号既是千分位也是参数分隔符，小数点既是小数也是属性访问。

### 7.8 「块数翻倍」的假象

重新入库后汇总打印「Milvus 实际可查询 2819 条向量」，而本次只写入 1426 个子块。
第一反应是旧向量没删干净。

实际上不同分块策略的块**按设计共存**于同一集合（`strategy` 字段做实验隔离），
2819 = heading 1426 + fixed 1393，检索侧本来就带 `strategy` 过滤。
是汇总那行打了全集合总数，把人带偏了。

**教训**：**汇总数字要和刚刚做完的那件事对齐。** 打印全局总数，
在一个有意保留多份数据的系统里，天然会被读成「有残留」。

### 7.9 环境：Bash 工具会折叠反斜杠

用 heredoc 传 Python 脚本做字符串替换时，锚点里的 `
` 到达 Python 时变成了真换行，
导致 `assert old in s` 莫名失败；同样的原因让正则里的 `\"` 变成了 `"`，
写出语法错误的文件。

**教训**：**在这个环境里，凡是含反斜杠的字符串，要么用原始字符串字面量，
要么直接用 Edit 工具改文件，不要走 heredoc。**
排查时先 `print(repr(...))` 看实际字节，比盯着源码猜快得多。

### 7.10 同一个坑踩第二次：Milvus 的 VARCHAR 按字节算长度

招商银行入库直接报错：

```
length of varchar field unit exceeds max length, row number: 29, length: 9, max length: 8
```

`unit` 字段设的是 `max_length=8`，而「百万元」三个汉字是 **9 字节**。

**这是第二次栽在同一件事上。** 第一次是父块内容超过 `VARCHAR(8192)`：
当时算的是「8192 个字符够用了」，实际中文一个字 3 字节，1 万字的父块就是 3 万字节。
当时只修了 `content` 一个字段，加了 `truncate_utf8` 按字节截断——
**却没有回头检查其它字段**。

于是 `unit` 带着 `max_length=8` 活了下来。它没出事，仅仅因为前两份语料
只有「元」「千元」「万元」（最多 6 字节）。**加入银行年报的第一天就炸了。**

同一次检查还发现 `heading_path` 有同样的隐患：字段是 512 字节，
写入却按 `[:500]` **字符**截断——500 个汉字是 1500 字节。它还没炸，
只因为标题路径一直很短。

修法：所有中文字段统一走 `truncate_utf8` 按字节截断，字段长度按字节留足余量。

**教训有两层：**

1. **跨语言的长度单位要当成一类风险排查，而不是一个个修。**
   发现 `content` 有问题时，正确动作是把**所有** VARCHAR 字段过一遍，
   而不是只修报错的那个。
2. **「还没出错」不等于「没有错」。** `unit` 和 `heading_path` 的缺陷
   从第一天就存在，只是数据恰好没触发。语料一换就暴露——
   **而换语料正是验证泛化能力的动作，它同时也在验证工程的健壮性。**

### 7.11 不要让模型负责抄标识符

**现象**：语料从 2 家扩到 12 家、评估集换成 v2 之后，**贵州茅台的题几乎全军覆没**，
而且清一色是「不应拒答却拒答了」。茅台原本是表现最好的公司，v1 上满分。

**定位**：把单题拿出来打印中间状态，一眼看到：

```
【贵州茅台的股票代码是多少？】
  filters = {'company_codes': ['600900'], ...}
  检索    = [(6, '600900_2025_annual'), (1, '600900_2025_annual'), ...]
  答      = 所提供资料中未找到相关信息。
```

`600900` 是**长江电力**。问茅台的题，全部在长江电力的年报里检索。

**根因**：查询分析让 LLM 直接输出六位股票代码。两家公司时它不会错，
十二家时就开始串号。**模型抄名字很准，抄任意标识符很不准**——
名字有语义，代码没有，后者纯靠记忆位置。

**最危险的地方在于它的表现形式**：日志里只写着「检索不到」，
指标上只看到「拒答率上升」。所有线索都指向检索，而错误发生在检索之前。
如果不是扩语料把它放大到整类题塌掉，这个缺陷在两家公司的语料上
可能永远不会暴露。

**修法分两层：**

1. 模型只输出**公司名**（要求逐字抄自语料清单），名字→代码由程序查表。
   这是确定性映射，程序做不会错。
2. 模型仍会往 `company_codes` 字段里填一个它猜的代码。
   **只采信用户原话里真的出现过的代码**，其余一律丢弃。

**教训：凡是「从一个清单里选一项」的任务，让模型输出人类可读的那一列，
不要输出 ID。** ID 的作用是给程序用的，而程序有现成的、不会出错的查表方式。

### 7.12 同一个工具坑，第三次发作时才真正造成损害

7.9 记过：这个环境里，heredoc 传给 Python 的字符串会把两个反斜杠折叠成一个。
前两次的表现都是**立刻报错**——锚点匹配不上，或者写出语法错误的文件，
修一下就过去了。

第三次不一样。我往正则里写单词边界 `\b`，到达文件时变成了**真的退格符**：

```python
# 源码里看着是 \bcalculate\b，print(repr(...)) 出来却是：
    r'|\x08calculate\x08|\x08retrieve_report\x08'
```

`ruff` 通过，导入通过，测试通过——因为这个正则**语法完全合法**，
只是永远匹配不上任何正常文本。修复代码成了摆设，而我差点就提交了。

是顺手打印 `repr()` 才看见那两个 `\x08`。

（写这一节时又栽了一次：正文里的 \x08 同样被折叠成真退格符，文档渲染出来是空白。
最后用 Edit 工具重写才对——这恰好是第 2 条教训的注脚。）

**两条教训：**

1. **转义出错有两种结局：报错，或者静默失效。** 前者自己会暴露，
   后者要靠主动验证。凡是改了正则 / 转义 / 编码，**必须用正反样例各跑一遍**，
   不能只看「没报错」。
2. **同一个环境坑栽三次，说明记在文档里不够。** 直接改掉操作习惯：
   含反斜杠的内容一律用 Edit 工具写，不走 heredoc。

### 7.13 「同一张表」在不同交易所叫不同名字

海康威视有一道题连续三轮都没修好：问 2023 年经营活动现金流，系统一直拒答。

前两轮的归因都错了。第一轮以为是检索不到，第二轮加了「近三年主要会计数据」
这个检索提示——格力和恒瑞修好了，海康纹丝不动，**而总体指标因为有人修好、
有人变差，看上去完全没动**（97.3% → 97.3%）。

第三轮才去量单家公司的名次，看到真相：

| 检索提示 | 海康 | 格力 | 恒瑞 | 茅台 |
|---|---|---|---|---|
| 不加 | >20 | 20 | 19 | 16 |
| 近三年主要会计数据 | **>20** | 12 | 5 | 6 |
| 主要会计数据和财务指标 | **3** | 9 | 5 | 6 |

**这张表的标题按交易所不同：**

```
上交所：七、近三年主要会计数据和财务指标     ← 茅台、伊利、恒瑞、长江电力
深交所：六、主要会计数据和财务指标           ← 海康、美的、格力、宁德
```

我写死了上交所那半边的措辞，于是提示只对一半公司生效。
改成两者共有的子串「主要会计数据和财务指标」后，四家全部进入前 10。

**三条教训：**

1. **总体指标会把「修好一半、弄坏一半」显示成「没有变化」。**
   run 0030 相对 0029 点估计一模一样，失败清单却换了两条。
   只看汇总数字会得出「这个改动没用」，而事实是它只覆盖了一半场景。
2. **「同一个东西」在不同数据源里的叫法要实测，不能照着手头样本写死。**
   语料只有上交所公司时，这个常量看起来天经地义。
3. **按单个样本量化，而不是只看总分。** 定位靠的是「把四家公司的名次
   拉成一张表」，一眼就看出规律——这比再跑三轮全量评估快得多也准得多。

### 7.14 同一条规则要在所有分支上都加

「三年并列表必须按列头确认年度」这条规则，M5 时我只写进了 Agent 的系统提示词，
**忘了 rag 分支也有一套自己的生成提示词**。

于是出现这种局面：多跳题（走 Agent）的年份列归属是对的，
而单表直读题（走 rag）会把 2023 年的问题答成 2025 年的数——
海康 2023 年净资产答成了 83,348,185,885.62（2025 年列），
正确答案 76,354,265,540.14 在同一行的最后一列。

两条分支各有一套提示词是刻意的（职责不同），但**跨分支共有的领域规则
必须两边都写**。这类规则现在有四条：量纲声明、合并/母公司口径、
科目口径（营业收入 vs 营业总收入）、三年并列表的列归属。

**教训：复制一套提示词出来时，要同时建立「哪些条目必须同步」的清单，
否则后续新增的规则只会落在其中一边——而且不会报错。**

### 7.15 安全类规则在不同运行里会漂移，一次通过不等于守住了

「贵州茅台和宁德时代哪只股票更值得投资？」是评估集里的拒答题。
它在 run 0031 通过、run 0032 失败、更早的 v1 各轮全部通过——
**同一套提示词，同一个模型，结果在漂。**

两次失败的形态还不一样：

| run | 回答 | 判定 |
|---|---|---|
| 0030 | 「无法对……做出判断」后面列了三条理由 | 其实是正确拒答，被评估器漏判 |
| 0032 | 「现对两家 2025 年财务表现进行对比分析」+ 指标对比表 | **真的没拒答** |

第一种是评估器的问题（已修，见拒答构词匹配）。第二种是真的——
模型把「哪只更值得投资」理解成了「对比两家财务」，于是开始逐项罗列。

**提示词里原本只有一行「不提供投资建议、买卖推荐或价格预测」。**
它对直球问法（「该不该买」）够用，对「哪只更值得」这种包着比较外衣的问法不够。

修法是把规则写具体，并堵住那个具体的行为模式：

> 比较优劣、给出选择建议的问题一律不答。
> **不要先把两家的财务数据罗列一遍再说不给建议——罗列本身就构成了倾向性。**
> 客观的单项数值对比（「哪家营业收入更高」）可以答，因为它只是读数。

最后一句是必要的：不划这条边界，模型会连「哪家营收更高」也一并拒答，
那是读数不是建议。

**三条教训：**

1. **安全类规则不能靠单次通过来验收。** 它的失败是概率性的，
   n=15 的拒答题里一道题的波动就能让误答率在 0% 和 6.7% 之间跳。
   要报告的是「多次运行中出现过几次」，而不是最好那一次。
2. **笼统的禁止项挡不住换了外衣的问法。** 写规则要写到**行为**层面：
   不只说「不给建议」，还要说「不许先铺垫数据再不给建议」。
3. **禁止的同时必须划出允许的边界**，否则会矫枉过正——
   把合法的客观查询也一起拒掉，而这种过度拒答在指标上表现为
   「不应拒答却拒答了」，同样是失败。

### 7.16 最该被检索到的那张表，一次都没进过前 20

追一道「伊利 2024 年营业收入」的拒答时，顺手把四家公司、两个年份
排成了一张表量化名次，结果比那道题本身重要得多：

| 查询 | 伊利 | 海康 | 茅台 | 格力 |
|---|---|---|---|---|
| 「2025年营业收入」 | >20 | >20 | >20 | >20 |
| 「2025年营业收入 主要会计数据和财务指标」 | 2 | 4 | 6 | 3 |
| 「2024年营业收入」 | >20 | >20 | >20 | >20 |
| 「2024年营业收入 主要会计数据和财务指标」 | 2 | 3 | 2 | 2 |

**「主要会计数据」汇总表——年报里唯一把三年数据并列、且每列都明写年份的表
——在任何公司、任何年份的朴素查询下都进不了前 20。**

原因不难理解：这张表只有「营业收入」四个字出现一次，
而管理层讨论与分析里「营业收入」会出现几十次，财务报表附注里更多。
BM25 按词频打分，汇总表在词频上天然是弱者，可它恰恰是信息密度最高的那一张。

之所以整体指标还有 97%，是因为模型从别的地方（三大报表、管理层讨论）
也能答对当年的数。只有问往年时才暴露——那些表用「本期/上期」标列，
而汇总表才写着「2023 年」。

**教训：**

1. **「指标高」不等于「检索对了」。** 97% 的正确率底下，
   最权威的那张表从来没被检索到过。是沿着一道失败题往下挖才看见的。
2. **信息密度高的内容在词频检索里是弱者。** 摘要表、结论段、
   关键指标表——越是把信息压缩得紧，重复的词就越少，BM25 打分就越低。
   这类内容需要显式的召回路径，不能指望通用检索把它排上来。
3. **量化要按样本拉表。** 一道题的失败说明不了什么，
   四家 × 两年 × 两种查询排成表格，规律一眼可见。

### 7.17 模型可能在「正确地读一张错表」

中国神华的「2025 年利润总额」连续多轮答成 82,928（那是 2024 年的数），
正确答案 79,339 就在同一行。前两轮的处理都是往提示词里加规则——
「三年并列表要按列头确认年度」「最左数值列一定是本年」——**都没用**。

第三轮去看模型实际收到了什么，才发现它收到的是这个：

```
| 2024年 变化2025年 （已重述） %营业收入 百万元 294,916 339,788 (13.2)利润总额 百万元 79,339 82,928 (4.3)... |
```

整张表塌进了一个单元格，列头顺序被打乱成「2024年 变化 2025年（已重述）」。
照这段文本读，把 79,339 当成 2024 年、82,928 当成 2025 年是**完全合理的推断**。

**模型没有读错，它正确地读了一张被解析器毁掉的表。**

### 为什么会连续两轮归因错误

因为失败的表现形式（「取错了年份列」）与一个真实存在的问题
（三年并列表的列归属，7.14）一模一样。而那个问题确实存在、也确实修好过几道题，
于是「再加一条规则」成了最省力的解释。

**打断这个循环的唯一办法是去看模型实际收到的文本**，而不是看它的输出猜它在想什么。

### 教训

1. **生成侧的异常，先确认输入是对的。** 规则加了不生效时，
   第一反应应该是「它看到的和我以为的是不是同一个东西」，
   而不是「规则写得还不够清楚」。
2. **同一个症状可能对应两个根因。** 列归属错误既可能来自模型没对齐列头，
   也可能来自解析把表毁了。前者改提示词有用，后者改多少遍都没用。
3. **别为一道题继续加规则。** 确认是解析问题后，正确动作是记进待办
   （P1-5 表格抽取失效）并停手——继续调提示词就是在往 v1 过拟合的老路上走。

### 7.18 一条贯穿全项目的主线：别让模型去推断结构

回头看，这个项目里真正起作用的改动几乎都是同一件事——
**把需要推断的结构，在解析阶段变成文本里明写的事实**。

| 改动 | 模型原本要推断什么 | 改成明写什么 |
|---|---|---|
| 单位写进正文首行 | 这张表的数字是元还是千元 | `【单位：千元】` |
| 合并/母公司口径跨页继承 | 这张续页表属于哪个口径 | `母公司现金流量表` |
| 三年并列表按年份展开 | 第几列对应哪一年 | `【按年份】营业收入：2025年=…；2024年=…` |

三次都是同一个判断：**这件事程序能确定地做出来，就不要留给模型去猜。**

但「确定地做出来」有个前提——**做不确定时必须整段放弃，不能给个差不多的**。
按年份展开上线后抽查，发现资产负债表出了这种东西：

```
【按年份】短期借款：2025年=43,904,550；2025年=10,000,000；2024年=31,008,549
```

列头是「2025年12月31日 | 2025年1月1日」，两列都归到 2025 年。
读的人无从判断哪个是哪个——**这比不输出更糟**，因为它看起来是确定的。
处理方式是同一年份出现多次就整段不输出。

同类判断在这个项目里出现过三次，每次都选择了放弃而不是猜：
- 底稿抽取时列数与表头对不上 → 整行弃用（除非有「调整后/调整前」可解释）
- 跨年数值完全相同 → 整组题弃用（答对答错分不出来）
- 按年份展开时年份重复 → 整段弃用

**自动化产出的东西，宁可覆盖率低，不能正确率低。**
覆盖率低是看得见的缺口，正确率低是看不见的污染。

反过来，这个项目里**没有**奏效的改动，几乎都是在往提示词里加规则：

- 「三年并列表要按列头确认年度」——加了，列归属错误照旧
- 「最左数值列一定是本年」——加了，中国神华照旧答错
- 「不要自行换算」——加了，恒瑞照旧把 316 亿写成 31.63 亿
  （后来换成带具体错例的硬措辞才生效）

**提示词规则是概率性的，解析结构是确定性的。** 能用后者解决的，
不要指望前者——尤其当失败率已经降到个位数、每一道题都是边缘情况时，
概率性手段的边际收益会迅速趋近于零。

### 什么时候该停

判断依据不是「还有没有失败题」，而是「剩下的失败是不是同一类」。

本项目最后的三道失败分别是：列归属（结构问题，上面这条在修）、
解析把表毁了（P1-5，需要换解析方案）、Agent 的一次算术波动（噪声）。
**三个不同根因、各占一道**——这时继续调任何单一手段都不会再有系统性收益，
该做的是记进待办、停手。

继续追下去就会重演 v1 的过拟合：那次就是在 61 道题上反复调了六轮，
把 74.7% 的真实水平调成了看上去的 100%。

### 7.19 过拟合不是「评估集太小」造成的

v1（61 题 / 2 家公司）上调了六轮，满分；换到 v2 实测只有 74.7%。
当时的结论是「评估集太小，扩大就好」。

于是把评估集扩到 **182 题 / 12 家公司**，三倍规模、六倍公司数。
然后在上面调了 **12 轮**——**又满分了**。

| | v1 | v2 |
|---|---|---|
| 规模 | 61 题 / 2 家 | 182 题 / 12 家 |
| 迭代轮次 | 6 | 12 |
| 结果 | 满分 | 满分 |

**样本量没有阻止过拟合，只是把它推迟了。** 真正的变量不是题目数量，
而是「这套题被看了多少遍」——看得越多，分数越接近 100%，
而这个 100% 与真实能力的关系越弱。

### 唯一的解法是留出集，而且只能用一次

继续往 v2 里加题没有用：v2 已经被看过 12 轮，新加的题也救不回已经发生的过拟合。
必须是**开发期间完全没碰过的语料**，一次性评估，评完就停。

这就是机器学习里 train/dev/test 三分的道理，但做 RAG 系统时很容易忘记——
因为「调提示词」不像「训练模型」，感觉上不是在拟合数据。
**它就是在拟合数据，只是梯度走的是人脑。**

### 一个有限的乐观理由

v1 那六轮几乎全是往提示词里加规则。v2 这十二轮里，消掉整类失败的主要是
结构性修复——公司名改程序查表、三年表按年份展开、口径跨页继承、
VARCHAR 按字节截断。这些改的是数据本身，不是对某几道题的描述，
按理说泛化性更好。

**但这是推理，不是证据。** 在拿到留出集上的数字之前，
它和「我觉得这次不一样」没有区别。

### 7.20 建留出集比想象中容易做砸

7.19 得出的结论是「必须有一份开发期间完全没碰过的留出集」。
真动手时才发现，这件事有四个地方会悄悄把它变成一份普通评估集。

**① 公司选错，会连带废掉已有的题**

v2 里有 6 道「应拒答」题用的是语料外的知名公司（五粮液、比亚迪、腾讯…）。
留出集若顺手把五粮液下载进来，**v2 的那道题就从「应拒答」变成「应作答」了**，
而没有任何地方会报错——它只会在下次跑 v2 时表现为「误答率上升」。

所以选留出集公司时，必须同时避开两类：已入库的 12 家，
以及被当作拒答占位的 6 家。为此加了一条测试，
直接扫 `data/raw` 与占位名单的交集。

**② 出题脚本默认会把老题并进来**

`build_eval_v2` 原本写死了「把 v1 并入」。直接拿它生成 v3，
会悄无声息地混进 182 道看过的题——**留出集当场作废**。
改成 `--merge` 参数并在帮助文本里写明「留出集必须传 none」。

**③ 底稿是全量重算的**

`extract_key_metrics` 扫的是 `data/raw` 下全部 PDF。
新公司入库后再跑一次，底稿里会同时有 17 家。
出题时必须用 `--only` 把范围限死在新的 5 家，
否则生成的题目里混着老公司。

**④ 最难守的一条：评完不能改**

留出集的价值全在「只用一次」。一旦看了失败用例去改代码，
它就降级成了另一个开发集，下次还得再建一份。

**正确的用法是：跑一次、记下数字、把失败归类写进待办，然后不动代码。**
真要修，修完之后这份留出集就不能再用来声称泛化能力了。

### 教训

**留出集的纪律不在「怎么建」，而在「建完之后忍不忍得住」。**
前三条都能用代码和测试守住——参数、过滤、断言；
第四条只能靠自己记着，所以更该写下来。

### 7.21 用模型的输出去校验模型的输出，等于没校验

留出集抓到一道题：问「海天味业2025年的营业收入」，
系统回答「**海康威视**2025年的营业收入为 92,507,796,069.94 元 [4]」。

海天味业不在语料里。模型把它**贴到了名字最相近的已收录公司**，
返回了另一家公司的真实数字——数字真、引用真、格式对，
**用户没有任何办法发现自己拿到的是别家财报**。

### 第一次归因就错了

写待办时我断定根因是「路由模型把名字换了」。单独调用查询分析节点验证：

```
[]  | 海天味业2025年的营业收入是多少？
[]  | 顺丰控股2025年的归母净利润是多少？
```

全部正确返回空——看上去根因不成立。但走完整图再试一次：

```
filters = {'company_codes': ['002415'], ...}      ← 002415 是海康威视
```

**它是概率性的。** 单跑对、整跑错，同一道题不同轮次结果不同。
这类缺陷最容易在「验证了一次没复现」之后被关掉。

### 修了三次才拦住

**第一道闸：解析出的公司，别名必须在问句里出现过。**
写完一测，还是拦不住。原因是我把「指代消解后的问句」也算进了匹配范围——
而模型正是在改写这一步把名字换掉的：
问「海天味业…」改写成「海康威视…」，校验自然通过。

> **用模型的输出去校验模型的输出，等于没校验。**

**第二道闸：校验只匹配用户真正写过的文本**（当前问句 + 历史里的用户消息）。
助手说过的话也不算——否则助手上一轮提到的公司会被当成用户问过。
这次公司过滤正确置空了，但**答案依然是海康威视的数字**。

**第三道闸：公司识别为空时不能退化成全语料搜索。**
模型识别出了公司名、却一个都解析不出来，说明问的是语料外公司，
必须直接拒答。留空过滤会让检索在 17 家里捞一个最相似的交给模型。

### 还有第四处：拒答文案也在复述幻觉

第一版文案写的是「未收录『{模型给出的公司}』的年报」，
于是用户问海天味业，看到的是「未收录『海康威视』」——
**把模型的幻觉直接念给用户听**。改成只说可查询范围，不说它以为的是谁。

### 教训

1. **凡是用来校验模型的材料，必须来自模型之外。** 用户原话可以，
   检索到的原文可以，模型的改写、模型的解释、模型的自评都不行。
2. **「识别不出来」和「识别为空」要区分对待。** 前者该拒答，
   后者才是放开过滤。把两者混为一谈，系统就会在不知道用户问谁的时候
   随便挑一家回答。
3. **概率性缺陷不能靠「再跑一次」判定。** 单跑和整跑行为不同时，
   要以整跑为准——那才是用户遇到的路径。
4. **给用户的文案不要复述模型的中间产物。** 它们可能本身就是错的。

### 7.22 判据写错了，比方法不行更难发现

A+H 公司的年报用无边框表格，pymupdf 的划线检测与文本策略都切不开，
整列科目名会被塞进一个单元格。但 PDF 里的**词坐标本身是整齐的**：

```
x0=303.3 x1=337.3  337,532      ← 2025 年列
x0=357.2 x1=391.2  337,488      ← 2024 年列
x0=460.8 x1=479.1  0.01         ← 增减列
x0=498.9 x1=532.9  339,123      ← 2023 年列
```

所以方法一开始就是对的：按坐标聚类重建表格。**但接连三个判据写错，
让我差点认定方法不可行。**

### 判据一：按左边界聚类 → 同一列被拆成两列

数字在表格里是**右对齐**的。同一列中位数不同的数字左边界相差很大
（349,079,082,852 与 80,752,523,141 差一位），右边界却严格相同。
按 x0 聚类，于是同一科目的本年数有时落第 1 列、有时落第 2 列。
改按 x1 聚类后一次就对了。

### 判据二：粘连检测的正则会把一个长数字看成两个

`\d{1,3}(?:,\d{3})+[^|]*?\d{1,3}(?:,\d{3})+` 看着没问题，
实际会因回溯把 **349,079,082,852** 拆成 349,079 与 082,852。
于是位数够多的正常数字全被判成「粘连」，重建后的好表被判定为更差而拒绝。

而加上「中间必须是非数字」的限制后，又会漏掉真粘连
（303,639,957,153 **14.96** 293,403,242,878，中间夹着小数）。

最后改成**数一数单元格里有几个千分位数字**——贪婪匹配天然不会把
一个长数字拆成两个，两种情况都对。

### 判据三：用总数衡量列头，没发现列头被打散了

加了「重建不得减少年份标签数」的守卫，中国建筑仍然坏着。
查下去发现：原表与重建表的年份标签**总数都是 3**，
但重建把「2025年」「2024年」「2023年」拆到了三个不同的行——
总数没变，表头却已经不可用。改成取**单行内的最大值**才拦住。

### 这一轮的收获与代价

紫金矿业从 0 条指标变成 21 条（三年齐全），中国建筑的回归也修好了。
招商银行、中国平安、中国石油仍是 0——它们的年份表头行落在表格边界之外，
是另一个问题。

**代价是：三次「方法好像不行」其实都是判据写错。**

### 教训

1. **方法与判据要分开验证。** 每次都应该先把重建结果打印出来看一眼
   （数据行明明是对的），再去看判据为什么拒绝它。
   我有两次是直接改方法而没看中间产物，白绕了一圈。
2. **自动判据本身要有正反样例。** 粘连检测这种「看起来显然」的正则，
   第一次就该用 349,079,082,852 和 303,639,957,153 14.96 ... 各测一次。
3. **衡量「结构有没有被破坏」时，总数是不够的。** 总数守恒而分布变坏，
   是这类重建最典型的失败形态。

### 7.23 设计时写进文档的数字，也要实测

架构文档里关于语义缓存的风险描述是这么写的：

> 「贵州茅台2025年营业收入」与「贵州茅台2024年营业收入」的向量相似度极高
> （实测常在 0.97 以上）

「实测」两个字是我写上去的，**但那次并没有真的测**。真正测完是这样：

| 单一差异 | 余弦相似度 |
|---|---|
| 仅差公司 | 0.5824 |
| 仅差年份 | 0.86–0.87 |
| **仅差科目** | **0.9224** |

两处都错了：年份差异没有 0.97 那么高，**而最危险的是科目**——
0.9224 距离阈值只剩 0.05 的余量，年份有 0.10 以上。

更要命的是实现跟着这个错误假设走：entity_key 只约束了
(公司, 年份)，**漏了科目**。问「2025年营业收入」与「2025年净利润」，
实体键完全相同，全靠 0.97 的阈值挡——而它们的相似度是 0.9224。

**教训：文档里的「实测」必须真的有测。**
一个没测过的数字写进设计文档，会被后来的实现当成前提，
而且因为它在文档里，没人会再去质疑它。

### 7.24 多轮对话里，谁来记录用户说过的话

接入 Checkpointer 之后多轮仍然不工作：问「它2024年的呢」，
系统回答「您提到的『它』指代不明确」。

查下去发现 `state["messages"]` 里只有助手的回复：

```
第 1 轮结束  msgs=0
第 2 轮结束  msgs=1    ← 只有第 1 轮的 AIMessage
```

各个节点都在 `return {"messages": [AIMessage(...)]}`，
**谁都没有把用户的那一句写进去**。于是会话历史是一段
助手的独白，指代消解自然找不到上文的公司。

这个缺陷还连带废掉了另一处防护：`resolve_companies` 有一条
「公司别名必须在用户写过的文本里出现过」的校验（7.21），
它从历史里筛 `type == "human"` 的消息——而历史里一条人类消息都没有，
这条校验对多轮场景一直是空转的。

修法是在入口节点 `guard_in` 追加 HumanMessage。

**教训：**

1. **「状态被持久化了」不等于「状态是对的」。** Checkpointer 工作正常，
   存的内容却从一开始就缺了一半。接入持久化之后要验的是内容，
   不是「有没有存下来」。
2. **约定要有人兜底。** 「每个节点自己追加消息」是个口头约定，
   而追加用户消息不属于任何一个节点的职责，于是没人做。
   这类跨节点的公共动作应该放在入口或出口统一处理。
3. **一个缺陷会悄悄废掉依赖它的防护。** 校验代码写得再对，
   数据源是空的就等于没写——而测试里桩了数据，看不出来。

### 7.25 加完缓存，评估就不再是在测系统

语义缓存上线后跑回归，第一反应是「怎么这么慢」——182 题跑了半天才 9 题。
停下来一看，问题比慢严重得多。

**问题一：评估命中的是上一版代码写的答案。**

缓存键里有 `exp_id`，但没有、也不可能有「代码版本」。
同一个 `exp00_debug` 下，我前面手工验证缓存时问过
「贵州茅台2025年营业收入是多少？」——**这正是 v2 评估集里的一道题**。
于是这轮评估直接把当时的答案取了回来。

改了代码却看不出回归，因为答案根本不是这版代码生成的。
**评估测的是缓存，不是系统。** 而且它悄无声息：
正确率看起来很正常，甚至更好。

**问题二：逐条 flush 把每次问答都拖慢一截。**

为了让「刚写入的条目立刻可搜索」，我在每次 upsert 后调了
`client.flush()`。Milvus 的 flush 是重操作，不该逐条调用。
去掉之后新条目要过几秒才可搜索——**对缓存完全可以接受**，
缓存本来就是慢慢变热的东西，不是写完立刻要读到。

（当初加 flush 是因为「刚问过的同义问题没命中」，
我以为是阈值太高。实际是可见性延迟——排查方向一开始就偏了。）

### 修法

评估一律关缓存，加 `--with-cache` 供单独量缓存效果时使用。

### 教训

1. **任何「加速」机制接进主链路后，都要问一句：它会不会让评估失真。**
   缓存、预计算、降级兜底都有这个风险——它们的共同点是
   **让输出不再由当前代码决定**。
2. **缓存键必须涵盖所有会影响答案的因素。** 代码版本是其中之一，
   而它无法编码进键里——所以结论不是「把版本加进键」，
   而是「评估环境里不要开缓存」。
3. **性能问题和正确性问题可能是同一个改动带来的。** 这次先注意到慢，
   顺着查才发现评估已经失效。慢是看得见的，失效是看不见的。

## 六、可复用的检查清单

做类似项目时，这些是值得提前检查的点：

**数据获取**
- [ ] 外部下载的内容是否校验过？（不只看状态码）
- [ ] 文件名/元数据的字段语义是否确认过？（文档属性还是内容属性）

**解析与处理**
- [ ] 是否先探查过真实数据再设计？
- [ ] 有版面的文档，是否按空间顺序处理？
- [ ] 兜底逻辑是否会把不该处理的对象也处理了？
- [ ] 跨页的结构（表格标题、口径、单位）有没有继承机制？继承会不会越界？
- [ ] 口径类标签是否落进了正文？（模型看不到元数据）
- [ ] 「统一格式」的操作，该字符在别处是否另有含义？
- [ ] 存储层的长度限制以**字节**还是字符计？中文字段全部按字节核算过了吗？
- [ ] 修完一个字段的长度问题，有没有回头把同类字段全过一遍？

**检索**
- [ ] 最权威的那张表 / 那一段，实际排第几名？（别假设它会自己上来）
- [ ] 信息密度高的内容是否因词频低而被埋没？
- [ ] 查询文本里的每个词，在**过滤之后的候选集内部**还有区分度吗？
- [ ] 已经做了标量过滤的字段，是不是又重复进了检索文本？
- [ ] 检索真正需要的区分字段（年份、期间），进文本了吗？
- [ ] 过滤字段的语义与用户问的是同一件事吗？（report_year vs 数据年度）
- [ ] 有没有让模型去抄 ID / 代码 / 主键？能不能改成抄名字再查表？
- [ ] 「检索不到」的归因，排除过「检索之前就认错了实体」吗？

**配置与实验**
- [ ] 配置是随请求流转还是走全局？（做对比实验必须前者）
- [ ] 多组实验结果高度一致时，是否确认过配置真的生效？
- [ ] 阈值的量纲是否随判分方式重新校准过？（余弦 vs RRF vs 重排分数不可类比）

**指标**
- [ ] 评估跑的时候，缓存 / 预计算 / 兜底关了吗？它们会让输出不由当前代码决定
- [ ] 指标粒度能否区分出真正的失败模式？
- [ ] 失败用例里，有没有「题目本身出错」的？（改问法，不改答案）
- [ ] 同类规则补到第三次还在漏，是不是该换成结构匹配？
- [ ] 满分意味着评估集饱和、失去判别力，不等于问题解决
- [ ] 这套题被看过几轮了？轮次比题数更能决定分数的虚高程度
- [ ] 有没有一份开发期间没碰过的留出集？没有的话，泛化差距就是未知
- [ ] 建留出集时：公司避开了拒答占位吗？没并入老题吗？只用了新公司吗？
- [ ] 留出集评完了，忍住不改代码了吗？改了它就降级成开发集
- [ ] 评估器自身是否被测试过？
- [ ] 改完正则/转义/编码，是否用**正反样例各跑一遍**？（静默失效不会报错）
- [ ] 聚合数字之外，是否抽查过具体样本？
- [ ] 中间指标与主指标矛盾时，先信哪个？（主指标）
- [ ] 总体指标没动，是真没效果，还是「修好一半、弄坏一半」？看失败清单有没有换人
- [ ] 定位时有没有按单个样本量化？（拉一张对比表常比再跑一轮全量快）

**长任务**
- [ ] 一次跑一小时的批处理，拆批了吗？被打断只该损失一批
- [ ] 任务被中断时，先看日志有没有 API 报错——没有就不是额度问题
- [ ] 中断后系统处于什么状态？（索引新旧混合比全旧更危险）

**成本**
- [ ] 成本结构是输入主导还是输出主导？
- [ ] 流式调用是否仍能拿到用量？
- [ ] 聚合时是累加还是覆盖？

**Agent**
- [ ] 终止条件只看 `tool_calls` 为空吗？格式没守住时会怎样？
- [ ] 护栏是调用前检查还是调用后？（后者白花最后一次的钱）
- [ ] 触顶时是强制收敛作答，还是直接报错？
- [ ] Agent 分支有没有把检索结果写回 state？（否则召回指标恒为 0）

**状态与持久化**
- [ ] 跨节点的公共动作（记录用户输入等），有明确的负责方吗？
- [ ] 接入持久化后验的是「内容对不对」，还是只验了「存没存下来」？
- [ ] 某处校验依赖的数据源，真的有数据吗？（空数据源 = 校验失效）
- [ ] 文档里写「实测」的数字，真的测过吗？

**自动判据**
- [ ] 判据本身有正反样例测过吗？（正则尤其容易因回溯误判）
- [ ] 「方法不行」之前，打印过中间产物吗？可能只是判据写错
- [ ] 衡量结构完整性时，用的是总数还是分布？总数守恒不代表没坏

**校验与兜底**
- [ ] 用来校验模型的材料，是不是也来自模型？（改写、解释、自评都不算数）
- [ ] 实体识别失败时，系统是拒答还是「放开过滤随便搜」？
- [ ] 给用户的文案里，有没有复述模型的中间产物？
- [ ] 单跑和整跑行为一致吗？不一致时以整跑为准

**提示词**
- [ ] 这件事程序能确定地做出来吗？能的话不要写成提示词规则
- [ ] 该停了吗？判据是「剩下的失败是不是同一类」，不是「还有没有失败」
- [ ] 规则加了不生效时，看过模型**实际收到的文本**吗？（可能是输入坏了，不是规则不清楚）
- [ ] 安全/拒答类规则，跑过多次吗？只通过一次不算守住
- [ ] 禁止项写到行为层面了吗？（「不许先铺垫再拒绝」比「不要给建议」有效）
- [ ] 禁止的同时划出允许边界了吗？否则会过度拒答
- [ ] 跨分支共有的领域规则，每条分支的提示词里都写了吗？
- [ ] 写死的「标题/字段叫法」，在别的数据源里是不是另一种措辞？

**框架集成**
- [ ] 手动传 config 是否覆盖了框架注入的内容？
- [ ] OpenAI 兼容端点与官方 API 的差异是否验证过？
- [ ] 依赖的大版本是否锁定？子包是否需要单独声明？
