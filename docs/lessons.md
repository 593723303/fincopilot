# 开发经验记录

这份文档记录 M0–M4 开发过程中遇到的真实问题、诊断过程与最终结论。

与 `benchmarks.md`（记录指标）和 `open-issues.md`（记录待办）不同，
这里记录的是**判断过程**：怎么发现问题、怎么定位、哪些判断是错的、
为什么错。代码可以重写，这些判断过程不能。

每条按「现象 → 定位 → 根因 → 教训」组织。

---

## 一、最危险的一类：静默失效

这类问题的共同特征是**不报错**。系统照常运行、日志干净、指标正常，
只是结果悄悄是错的。它们比崩溃危险得多——崩溃会立刻暴露，静默失效可以潜伏很久。

### 1.1 实验配置没有流转，三组消融全部作废

**现象**：三组消融实验（重排、放宽截断、换模型）的指标几乎一模一样。

**当时的判断（错的）**：这些优化都没用。差点据此收手。

**定位**：换模型后成本应该降到四分之一，实测却几乎没变——这不合理，顺着查下去：

```python
# run.py
exp = load_experiment(args.exp)     # 读了 --exp 指定的配置
# 节点内部
exp = load_experiment()             # 无参数，读的是环境变量 EXP_ID
```

**根因**：`--exp` 只影响评估记录，不影响实际运行。三组实验跑的全是同一个基线配置。

**后果**：如果没查，会错过后面 **+21.3 个百分点**的改进，并得出「重排和放宽截断都没用」的错误结论。

**教训**：
- **配置必须随请求流转，不能走全局状态**。全局配置在单实验时毫无问题，
  一旦要做横向对比就会静默失效——它不报错，只是让所有实验变成同一个。
- **当多组实验结果高度一致时，先怀疑实验本身没生效**，而不是急着下结论。

### 1.2 下载"成功"但内容完全无关

**现象**：下载了两家公司的年报，文件名正确、大小正常。

**定位**：解析统计完全相同（307 页、362 个表格、相同字号分布）——不可能是巧合。
比对 SHA256，两个文件完全相同；读首页，内容既不是茅台也不是宁德，而是第三家公司。

**根因**：巨潮查询接口的 `stock` 参数必须是 `"{code},{orgId}"` 格式。只传 code 不会报错，
会被静默忽略，接口返回全市场最新公告。

**教训**：
- **下载成功 ≠ 下载正确**。凡是从外部获取数据，都要校验内容而非只看状态码。
- 修复时加了强制校验：读 PDF 首页，确认包含目标公司代码，否则删除文件并报错。

### 1.3 成本统计悄悄归零

**现象**：修完流式输出后，成本统计里 `light` profile 变成 `0.0`。

**定位**：单独调用节点能拿到用量，放进图里就是 0。差异只有 config。

**根因**：在 `astream_events` 环境下，LangChain 会把 `ainvoke` 也转成流式执行
（为了产生 token 事件），而**流式响应默认不回传 token 用量**，需要显式 `stream_usage=True`。

**教训**：
- 这不是个别节点的问题，是所有 LLM 调用的共性，**应该在 Provider 层统一解决**，
  逐处添加迟早会漏。
- 成本统计出现「恰好是 0」的值时要警惕——真实用量极少正好为零。

### 1.4 用量累加变成覆盖

**现象**：同一个模型被调用两次，账面上只有后一次的花费。

**根因**：
```python
"by_profile": {**prev.get("by_profile", {}), **cur.get("by_profile", {})}
```
字典展开对同名 key 是**覆盖**而非累加。而且 `query.py` 和 `rag.py` 各写了一套合并逻辑。

**教训**：聚合逻辑只应有一处实现。两处相似的实现，迟早会有一处是错的。

## 二、指标会说谎

这一类问题更隐蔽：**指标本身就是错的**，而人会倾向于相信数字。

### 2.1 覆盖率 100%，其中一部分是错的

**现象**：表格量纲标注覆盖率做到了 100%，看起来完美。

**定位**：抽查了几条，发现：
- 「备查文件目录」这种纯文字表被标成「单位：元」
- 董监高持股表标成「单位：元」，而表格第一行白纸黑字写着「单位：股」

**根因**：兜底逻辑无条件给所有表格套上文档主导量纲，包括非数值表；
且只看表格上方，没有提取表格内部的单位声明。

**结果**：修复后覆盖率**从 100% 降到 79–88%**，但正确性大幅提升。

**教训**：**指标下降反而是进步**。100% 的覆盖率是把错误答案也算进去的结果。
不要只看聚合数字，要抽查具体样本。

### 2.2 文档级召回 93.9%，页码级召回只有 38.8%

**现象**：`Recall@K` 高达 93.9%，但大量问题答不出来。

**根因**：召回是以 **doc_key** 为粒度算的——茅台年报里任何一个块命中都算 100%。
它无法区分「检索到 p6 主要会计数据」和「检索到 p150 无关附注」，
**而后者正是当时的主要失败模式**。

改成页码粒度后，真实召回是 **38.8%**。

**教训**：**指标的粒度决定它能发现什么问题**。粒度过粗的指标不是不精确，
而是会主动掩盖问题，让人以为一切正常。

### 2.3 评估器自己有缺陷，误答率虚高到 50%

**现象**：误答率 50%，看起来系统严重违反拒答约束。

**定位**：看实际回答，那两条「误答」其实都是正确拒答：

```
"我无法提供投资建议。作为财报分析助手，我可以帮助您解读财务报表..."
"我无法提供腾讯控股2025年的营业收入预测，因为...未在已收录的年报中出现"
```

**根因**：拒答识别的关键词表只收了「未找到」类说法，漏了「我无法提供」。

**第二次踩坑**：补全词表后改为全文匹配，又把两道正确题判成了拒答——

```
"贵州茅台的股票代码是600519。 我可以帮助您分析财报数据，但无法提供实时行情..."
                                                      ↑ 被这句误伤
```

**最终解法**：只匹配**第一句**。真正的拒答第一句就表态，免责声明在末尾。

**教训**：
- **评估器自身也需要被测试**。评估集和判定规则错了，所有指标都是假的，
  而且错得很隐蔽——数字看起来完全正常。
- 修改判定规则后**必须回跑历史用例确认没有反转**。

### 2.4 标注过严，让好结果显得很差

**现象**：页码召回为 0 的题，很多 `is_correct = true`（答对了）。

**根因**：同一个数据在年报多处出现（p6 主要会计数据、p9 主营业务分析），
标注只写了 p6，但模型从 p9 答对同样是对的。

**教训**：中间指标受标注方式影响极大。**主指标必须是端到端正确率**——
中间指标再漂亮或再难看，都可能是标注造成的假象。

## 三、语义错位：字段名对，含义不对

### 3.1 report_year 是文档的年度，不是数据的年度

**现象**：问「2024年营业收入」返回空，拒答。

**根因**：一份 2025 年报含 2023–2025 三年数据，但它的 `report_year` 只有 2025。
按 `report_year == 2024` 过滤必然为空。约四分之一题目因此被误拒。

**排查时的陷阱**：因为**检索阶段就返回空，相关度阈值根本没被触及**，
我先花了一轮去调阈值，结果「误拒」反而从 14 条变成 15 条——完全是错误方向。

**教训**：字段名相同不代表语义相同。做过滤前先问一句：
**这个字段描述的是文档的属性，还是内容的属性？**

### 3.2 标题与内容错配

**现象**：某个块 `heading_path = 十、非经常性损益`，而内容是「九、分季度财务数据」。

**根因**：解析循环先遍历整页所有文本行更新标题追踪器，再处理表格，
**表格拿到的是整页最后一个标题**。

**解法**：按页面纵向位置把文本段与表格混合排序，顺序处理。错配降为 0，
且标题路径从一级变完整三级。

**教训**：处理有版面的文档时，**元素的空间顺序即语义顺序**，不能按类型分批处理。

## 四、调试方法

比具体问题更可复用的是方法。

### 4.1 先探查，再设计

写 PDF 解析器之前先写了探查脚本，结果**推翻了三个假设**：

| 原假设 | 真实数据 |
|---|---|
| 表格是需要特殊处理的少数情况 | 75–85% 的页面含表格 |
| 量纲在文档内混用 | 跨公司系统性差异（茅台全用元，宁德全用千元） |
| 单位声明就在表格上方 | 只有 52–64% 如此 |

如果凭假设直接写，三条都会写错。**凭想象写解析器是这类任务最容易返工的地方。**

### 4.2 隔离变量，单独测量

定位截断问题时，没有去跑完整评估（慢且贵），而是写了只测召回的脚本
（不调用生成模型，成本接近零）：

```
检索 top_k=5    63.3%
检索 top_k=20   95.9%
检索 top_k=50   98.0%
```

一下就看出检索本身没问题。

### 4.3 分阶段测量，定位损失发生在哪一步

```
检索 top20   95.9%
截断 top5    44.9%   ← 一步损失 51 个百分点
父块还原     44.9%   ← 无额外损失
```

**信息不是没检索到，是检索到之后被丢掉了。** 这一步测量直接定位了真正的瓶颈。

### 4.4 静态检查要用 AST，不要用字符串匹配

给「禁止节点调用无参 `load_experiment()`」写防回归测试时，第一版用字符串匹配，
结果把 `state.py` **文档字符串里**的说明性提及也报成了违规——
而那段文字恰恰是在解释为什么不能这么调用。

改用 `ast.parse` 查找真实的函数调用节点后才准确。

**教训**：注释和文档字符串里出现函数名是常态，尤其是在解释该函数用法的地方。
静态检查必须基于语法树。

### 4.5 不信任何未经验证的数字

这个项目里被证伪的"显然正确"的判断：

| 判断 | 实际 |
|---|---|
| 量纲覆盖率 100%，做得很好 | 其中一部分标错了 |
| 文档召回 93.9%，检索没问题 | 页码召回只有 38.8% |
| 误答率 50%，拒答约束失效 | 评估器识别不全，实际是 0% |
| 三个实验指标一样，优化没用 | 配置没生效，三个跑的是同一个 |
| 成本估算 ¥0.03 | 实测 ¥0.003，差一个数量级 |
| 重排能解决排序问题 | 各截断深度下均无帮助，部分更差 |
| 标题分块优于定长分块 | 无显著差异，定长反而略高 |
| 强模型质量更好 | 与便宜模型无显著差异，成本差 4.8 倍 |

**共同点：每一个都是「看起来合理的数字」或「看起来合理的假设」。**

后三条尤其值得注意——它们不是算错了，而是**沿用了通用最佳实践却没在
自己的数据上验证**。重排、语义分块、强模型都是 RAG 的标配建议，
在这个场景里全部落空。

## 五、优化达标的完整过程

目标：提升答案正确率。起点 65.6%，终点 86.9%（+21.3 点，置信区间不重叠）。

过程**经历了三次方向反转**：

### 第一次：以为是相关度阈值

观察到大量「不应拒答却拒答了」，算了一下 RRF 分值范围：

```
两路都排第一  2/61 = 0.0328
仅一路命中    1/61 = 0.0164   ← 低于阈值 0.02，直接被拒
```

阈值确实错了，改成 0.010。**结果误拒反而从 14 条变成 15 条。**

教训：阈值错是真的，但不是主因。**修了一个真实的 bug 不代表修了关键的 bug。**

### 第二次：以为是排序

诊断发现检索系统性偏向财务报表附注（p60–120）而非摘要表（p6–7）——
附注里科目名出现频率高，摘要表的 BM25 分数被稀释。看起来是典型的排序问题。

接入重排。**正确率一点没动。**

隔离测量后发现，重排在所有截断深度下都没帮助，top_n=10 时甚至低 9 个百分点。
gte-rerank 是通用语义模型，对中文财报表格的结构化内容判断不如 RRF 融合——
它的分数分布也印证这点（实测集中在 0.11–0.16，区分度极低）。

教训：**负面结果也是结果**，而且要有数据支撑才站得住。

### 第三次：真相是截断深度

分阶段测量定位到 `top_n=5` 的截断一步丢掉 51 个百分点。
放宽到 15 并同步扩大上下文预算后：

| 指标 | 改前 | 改后 |
|---|---|---|
| 正确率 | 65.6% [54.1, 77.0] | **86.9% [78.7, 95.1]** |
| 页码召回 | 38.8% | **88.8%** |
| 表格数值题 | 53.3% | **93.3%** |

置信区间不重叠，是整个项目第一个可以正式声称的提升。

### 最终的消融结论：三个"标配优化"全部无效

四个因子各自的边际贡献：

| 因子 | 效果 | 结论 |
|---|---|---|
| 截断深度 top_n 5→15 | **+21.3 点**，区间不重叠 | 唯一显著因子 |
| 生成模型 plus→flash | -1.7 点，成本降至 1/4.8 | 质量持平，显著省钱 |
| 分块策略 heading→fixed | +1.6 点，区间重叠 | 无显著影响 |
| 重排 关→开 | -1.7 点，成本 +6% | 无效 |

**重排、语义分块、强模型——这三个被广泛推荐的 RAG 优化手段，在本场景
全部没有显著收益。真正起作用的是一个很少被讨论的参数：送进上下文的块数。**

分块策略那条还推翻了架构文档自己的假设（ADR-005 假定标题分块更优）。
事后看原因很清楚：75–85% 的页面含表格，而表格是整块处理的，
根本不经过文本分块逻辑。**最该优化的地方，往往不在通用最佳实践的清单上，
而在你这个场景的数据特征里。**

处理方式是把 heading 策略的保留理由从「检索更准」改成
「产出的 heading_path 对引用展示与排查有价值」——
一个诚实的降级，而不是继续用一个站不住的理由。

### 顺带的成本优化

把生成模型换成 qwen-flash：质量无显著差异（85.2% vs 86.9%，区间大幅重叠），
误答率反而更低，**单题成本从 ¥0.0062 降到 ¥0.0013**。

原因：本场景输入远大于输出（约 4000 入 / 100 出），
而 flash 的输入单价只有 plus 的五分之一。**先看清成本结构，再决定省哪一头。**

## 六、可复用的检查清单

做类似项目时，这些是值得提前检查的点：

**数据获取**
- [ ] 外部下载的内容是否校验过？（不只看状态码）
- [ ] 文件名/元数据的字段语义是否确认过？（文档属性还是内容属性）

**解析与处理**
- [ ] 是否先探查过真实数据再设计？
- [ ] 有版面的文档，是否按空间顺序处理？
- [ ] 兜底逻辑是否会把不该处理的对象也处理了？

**配置与实验**
- [ ] 配置是随请求流转还是走全局？（做对比实验必须前者）
- [ ] 多组实验结果高度一致时，是否确认过配置真的生效？
- [ ] 阈值的量纲是否随判分方式重新校准过？（余弦 vs RRF vs 重排分数不可类比）

**指标**
- [ ] 指标粒度能否区分出真正的失败模式？
- [ ] 评估器自身是否被测试过？
- [ ] 聚合数字之外，是否抽查过具体样本？
- [ ] 中间指标与主指标矛盾时，先信哪个？（主指标）

**成本**
- [ ] 成本结构是输入主导还是输出主导？
- [ ] 流式调用是否仍能拿到用量？
- [ ] 聚合时是累加还是覆盖？

**框架集成**
- [ ] 手动传 config 是否覆盖了框架注入的内容？
- [ ] OpenAI 兼容端点与官方 API 的差异是否验证过？
- [ ] 依赖的大版本是否锁定？子包是否需要单独声明？
