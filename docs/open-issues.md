## P0-1 · 评估集样本量不足，指标无判别力

**进展**：评估集已从 15 题扩到 **61 题**（`eval/datasets/v1.jsonl`），
区间半宽从 ±20 点收窄到 **±11.5 点**，可检测 20 点级别的改动。
但仍不足以检测 10 点级别的精细调优。目标 320 题。

**已解决（2026-10-05）**：评估集换为 **v2，182 题 / 12 家公司**
（`eval/datasets/v2.jsonl`），区间半宽收窄到约 ±6 点，判别力恢复。
同一套代码在 v1 上满分、在 v2 上只有 74.7%——**22.6 点的落差就是
对 61 道题过拟合的代价**，印证了当时拒绝把满分写成「准确率 100%」是对的。

新的限制取而代之：
- v2 的 124 题为自动生成，分层抽检 20/20 正确，但只抽了 16%
- 招商银行、中国平安、中国石油三家**没有题**（P1-5：表格抽取失效），
  语料覆盖 12 家而评估只覆盖 9 家，对外报指标必须说明
- 目标仍是 320 题，并补齐这三家

**2026-10-07 更新**：v4 留出集（86 题 / 5 家未接触公司）已评估，
正确率 83.7%，标注有效子集 94.7%。判别力问题已解决——
这个指标现在能区分好坏了，而且立刻查出了一个标注缺陷和两个系统缺陷。
下一份留出集是 **v5**，构建时必须重跑 `extract_key_metrics`
（v4 的底稿生成于口径过滤之前）。

**以下为 v1 时期的记录。** M5 结束时 v1 上已连续两次满分
（run 0026 / 0027，61/61），意味着：

1. **指标已失去判别力**——此后任何改动，无论变好变坏，在这个指标上都看不出区别
2. **存在明确的过拟合**——M5 期间连续六轮「看错题 → 改提示词 → 重跑」，
   提示词是对着这 61 道题调出来的，泛化能力没有被验证

因此满分**不得**被表述为「系统准确率 100%」，只能说
「在这 61 道人工核验过的题目上，经六轮针对性修复后不再有失败案例」。
在评估集扩大之前，所有进一步优化都是盲调。

**现状（历史记录）**：种子评估集 15 题，正确率 73.3%，95% 置信区间 `[53.3, 93.3]`，**半宽 20 个百分点**。

**影响**：这是目前最关键的限制。在这个区间宽度下，任何小于 20 个点的差异都无法与随机波动区分，意味着：

- 跑 `exp01_baseline` 对照（假设 60%），区间约 `[40, 80]`，与基线完全重叠 → 只能得出「无显著差异」
- 做完重排（假设 85%），区间约 `[67, 100]`，仍然重叠 → 无法声称有提升

**所有消融实验的结论在当前样本量下都不成立。**

**额外的硬约束**：评估集一旦变更，历史指标全部作废——指标不可比，必须重跑。
因此顺序只能是「先定评估集 → 再跑对照与优化」，反过来会白跑。

**样本量与判别力的关系**（正确率在 70% 附近时的估算）：

| 题数 | 区间半宽 | 能检测的最小差异 |
|---|---|---|
| 15 | ±20 点 | 基本检测不出任何东西 |
| 80 | ±10 点 | 20 点级别的改动（如重排） |
| 320 | ±5 点 | 10 点级别的精细调优 |

**处理计划**：
1. 先扩到约 80 题（基于现有两份年报），支撑 M4 的主要结论
2. FinGLM 标注数据到位后扩到 320 题，用于交叉消融与逆向消融

**验收标准**：实验记录表中任何声称「有提升」的行，其置信区间必须与对照行不重叠。
达不到的只能记录为「无显著差异」。

## ✅ P0-6 · 科目名跨行折断导致整词检索不到（已修复）

**来源**：v4 留出集 run 0045。广发证券 1 对 10 错，多数是标注缺陷，
但有一条是真缺陷：问 2023 年经营活动现金流，**数据在库里却拒答了**。

### 定位过程（两次判断错误，都记下来）

复现后看召回列表：只有第 20 页「主要会计数据（母公司）」，
没有第 19 页「主要会计数据（合并报表）」。

**第一次判断错**：我 grep 整份 PDF 找「经营活动产生的现金流量净额」，
命中页里没有第 19 页，于是得出「合并口径的 2023 年现金流年报根本没披露，
系统拒答是对的」。错在——第 19 页的科目名**被换行折断**成
「经营活动产生的现金流」+「量净额（元）」，整串 grep 当然匹配不到。
改看该页所有「（元）」结尾的行，才发现有一行残片「量净额（元）」。

**第二次判断错**：我用 `getattr(blk, "summary_table")` 检查，
得到 `None`，以为第 19 页没被标成汇总表。实际标记存在 `blk.flags` 里，
查法本身就是错的——第 19 页一直都有 `summary_table` 标记。

### 真正的根因

年报的「项目」列往往很窄，长科目名折成两三行，数值只落在第一行：

```
| 经营活动产生的现金流 | -27,780,960,722.97 | 9,970,809,011.81 | -8,918,975,156.38 |
| 量净额（元）         |                    |                  |                   |
```

后果是**整词在块里从不出现**。BM25 打不中，向量表示也被削弱。
而同一份年报第 20 页的母公司表列宽些、科目名完整，于是检索稳定地
选中了错的那张——母公司表里没有合并口径的数，模型据此拒答。
正确答案 **-8,918,975,156.38** 就在没被召回的那张表里。

### 修复

`app/rag/pdf_parser.py` 新增 `merge_wrapped_labels()`，
在表体渲染前把「续行」并回数据行。判定续行要同时满足四个条件：
非空格全是中文、行内无数值格、非空格不超过两个、上一行有数值格。
最后一条挡住了紧跟表头的子列头行——表头里的「2025 年」不算数值，
所以 `调整前 / 调整后` 那行不会被并进表头。

实测第 19 页修复后，三个长科目名的整词出现次数从 0 变成 2，
表头的「增减」「调整前/调整后」行未受影响。单元测试覆盖三类误伤场景。

**已全量重新入库**（22 份）。按留出集纪律，v4 已逐题看过，
**本修复的收益只能在 v5 上测量**。

## P0-3 · 检索结果不稳定，给评估引入噪声

**v2 实测（2026-10-05）**：同配置多轮运行，总体正确率在 **97.3%–98.4%** 之间，
相当于 1–2 道题的差异；拒答类（n=15）误答率在 **0% 与 6.7%** 之间反复，也就是一道题。
另有 0–1 道题栽在瞬时网络错误上——已在评估器里对连接/超时类加两次重试，
把这部分噪声剔掉，业务错误一律不重试。

**报告口径**：这类指标应给出多轮区间而非最好的一次，安全相关的拒答尤其如此。

**历史现象**：同一道题两次运行得到不同答案（研发投入题分别答出 117,009,982.85 与 109,689,625.09），
两个数字来自不同的表。生成温度为 0.1，波动来自混合检索的 RRF 排序在边界上不稳定。

**影响**：噪声会叠加到所有对比上。在小样本下，一次运行的差异可能完全来自这种波动而非配置改动。

**处理计划**：
1. 评估时对同一题多次运行取多数，或固定检索侧的随机性
2. 在实验记录中单独报告「运行间方差」，让读者知道噪声水平

**验收标准**：同一配置连续两次完整评估，总体正确率差异应小于区间半宽。

## P1-6 · 「重述后/重述前」拆列表的年份归属

**现状**：中国神华、长江电力的「主要会计数据」表把上年与前年各拆成
「重述后 / 重述前」两列，数据行因此比表头多出几列：

```
表头    |  | 2025年 | 2024年 |  | 2025年比2024年增减(%) | 2023年 |  |
子列头  |  |  | 重述后 | 重述前 |  | 重述后 | 重述前 |
数据行  | 利润总额 | 79,339 | 82,928 | 85,793 | (4.3) | 85,035 | 87,176 |
```

**qwen-flash 与 qwen-plus 都读错**（都答成 82,928，即 2024 重述后），
说明这是结构问题而非模型能力问题——需要把表头与子列头合并后才能对齐。

**当前处理**：抽取底稿时只取最左数值列（当年，不存在调整前后之分），
其余整行弃用；生成侧尚未加同样的规则。

**处理计划**：
1. 短期：把「最左数值列一定是本年」写进两条分支的生成提示词
2. 长期：解析阶段把子列头并入表头（`2024年重述后`），让列归属不依赖模型推断

## ✅ P2-2 · 索引更新：改了代码不会自动重算（已修复）

**原记录**是「增量更新简化为全量重建」，实际问题比这更严重。

入库的幂等检查只比对 PDF 字节哈希，于是**文件没变、但解析代码变了**
这一整类变化会被直接跳过——索引静默停在旧版本上，
而且没有任何指标看得出来。已造成两次事故：

| 时间 | 改了什么 | 后果 |
|---|---|---|
| P1-7 | 给汇总表打 `table_summary` 标记 | 17 家公司索引里从未出现该标记，藏了一天 |
| 2026-10-08 | 修科目名跨行折断 | 必须手动记得 `--force`，忘了就白改 |

**修复**：新增 `app/rag/fingerprint.py`，指纹 = 解析器与分块器源码哈希
+ 分块配置 + embedding 模型与维度。跳过条件改为三者同时成立：
文件没变、流水线指纹没变、上次入库成功。
新增 `documents.pipeline_hash` 列（迁移 `c7d4e2a91f36`）。

配套两个入口：

- `--prune` 清掉源文件已删除的文档——此前入库只有「加」和「改」没有「减」，
  删掉 PDF 后它的向量会永远留在库里被检索命中
- `--stamp-pipeline` 给确知是用当前流水线跑出来的语料补写指纹，
  避免加列那一刻把整个语料判成过期、白白重算一遍

取舍：按整文件哈希，改注释也会触发重算。两边代价不对称——
漏算是索引静默过期且测不出来，多算是 ¥1 量级的重新 embedding。
详见 `lessons.md` 7.32。

**仍未做**：真正的增量更新（只重算受影响的块）。
当前粒度是「整份文档重算」，22 份全量约 40 分钟。
语料规模上到百份量级时需要再细化，现在不构成瓶颈。

## ✅ P0-4 · Recall@K 粒度过粗（已解决）

**原问题**：以 `doc_key` 为粒度，茅台年报任何一个块命中都算 100%，
93.9% 的数字完全掩盖了真实情况。

**解法**：改为页码粒度（容差 ±1 页，照顾跨页表格），同时保留文档级
作为「文档过滤是否正确」的下限指标。

**结果**：真实召回暴露为 **38.8%**，与文档级的 93.9% 相差 55 个百分点。
正是这个指标让后续的截断深度问题得以定位。

**遗留**：`expected_pages` 标注偏严——同一数据在年报多处出现
（p6 主要会计数据、p9 主营业务分析），只标了 p6，从 p9 答对会被记为召回失败。
应改为「可接受页集合」。当前页码召回因此被系统性低估，
作为趋势指标仍可用，但不应作为绝对值对外引用。

## ✅ P1-1 · 重排（已实现，经测试后放弃）

**结论：对本场景无效，已在所有推荐配置中关闭。**

实测数据（`exp05_rerank_wide` 对 `exp04_wider`）：正确率 -1.7 点、

隔离测量进一步确认，gte-rerank-v2 在各截断深度下都没有帮助：

| 5 | 44.9% | 42.9% |

代码保留在 `app/providers/reranker.py`，配置开关可随时启用。
若后续更换重排模型（如专门的中文或表格重排模型），可直接复用。

## ✅ P1-2 · Agent 分支（已实现）

**已落地**：ReAct 循环 + 两个工具（`retrieve_report` / `calculate`）+ 三道护栏
（步数 8、连续工具失败 3、成本预算 ¥0.15），触顶时**强制收敛作答而非报错**。
`calculate` 是基于 AST 白名单的受限求值，拒绝名称、属性、下标、推导式、lambda，
并对指数设上限（`9**9**9` 这类表达式能用极小输入耗尽内存）。

**效果**：多跳推理 62.5%(5/8) → 100%(8/8)。

**遗留**：
- Checkpointer（可恢复会话）、长期记忆、HITL `interrupt()` 尚未接入 → M6
- 小模型会把工具调用写成正文（结构化 `tool_calls` 为空），已加拦截并计入工具失败，
  但根因在模型侧，换模型时需重新验证
- `query_financials` / `plot_chart` 两个工具未实现（前者依赖 P1-4）

## ✅ P0-5 · 语料外公司被「贴」到相近公司（已修复）

**三道闸**（每道都是上一道没拦住才加的，详见 `lessons.md` 7.21）：
① 公司别名必须在**用户写过的文本**里出现过——第一版把模型改写后的问句
也算进匹配范围，完全拦不住，因为模型正是在改写时把名字换掉的；
② 校验只匹配当前问句与历史里的用户消息，助手说过的话不算；
③ 识别出公司名却一个都解析不出来时直接拒答，不能留空过滤——
留空会让检索退化成全语料搜索，在 17 家里捞一个最相似的交给模型。

另修拒答文案：原本会复述模型贴错的公司名，等于把幻觉念给用户听。

**原问题记录**

**留出集实测（run 0040）**：问「海天味业2025年的营业收入是多少？」，
系统回答「**海康威视**2025年的营业收入为 92,507,796,069.94 元 [4]」。

海天味业不在语料里，正确行为是明确说明未收录。
但模型把它贴到了名字最相近的已收录公司，**返回了另一家公司的真实数字**。

**这比普通答错严重**：数字是真的、引用是真的、格式是对的，
从输出上看不出任何异常。用户没有办法发现自己拿到的是别家的财报。

**根因**：查询分析的提示词要求「公司名必须逐字抄自可用语料列表」。
面对列表里没有的名字，模型选择了最相似项，而不是留空。
`resolve_companies` 的包含匹配兜底也可能放大这个问题
（「名字没精确命中时退一步做包含匹配」）。

**处理方向**（尚未实施）：
1. 提示词里把「语料外就留空」写成硬性要求，并给出反例
2. `resolve_companies` 对模型给出的公司名做**精确或别名命中**校验，
   不命中就返回空，不做包含匹配兜底
3. 更稳的做法是加一道校验：若问题里出现了某个公司名，
   而它不在已收录别名表中，直接走拒答，不交给检索

**验收**：必须用新的留出集验证——v3 已经因为这条被看过了。

## ✅ P1-9 · Agent 心算（已修复）

结论里出现算出来的数（百分比）却一次 `calculate` 都没调过，判定为心算并打回。
**只打回一次**，再犯则接受并标记 `agent_mental_arithmetic`——
反复打回只会多烧调用、最后仍输出同一个心算结果，不如留痕让评估暴露。

**原问题记录**

**留出集实测（run 0040）**：问万华化学 2025 年营业收入同比，
模型检索到的两个数完全正确（203,234,573,814.42 与 182,069,119,160.94，
正确答案 11.62%），但直接给出「增长了 2.74%」——没有调用 calculate 工具。

提示词里已有「**任何算术都必须走 calculate 工具**」，
但这是概率性约束，压不住。

**处理方向**：在 Agent 侧做结构性约束而非提示性约束，例如
回答里出现百分数却没有任何 calculate 调用记录时，强制回退重算。
这与「别让模型推断结构」（lessons 7.18）是同一个思路：
**能用代码判定的事，不要交给提示词。**

## ✅ P1-3 · 语义缓存（已实现并启用）

两级：精确缓存（Redis，24h TTL）+ 语义缓存（Milvus，实体硬约束）。

**实测效果**：同一问法 3429 → 872 ms，不同问法 1592 ms，
单题成本 ¥0.0018 → ¥0.0003（**降 83%**）。

**实体约束的依据是实测相似度，不是设计时的直觉**：

| 单一差异 | 余弦相似度 |
|---|---|
| 仅差公司 | 0.5824 |
| 仅差年份 | 0.86–0.87 |
| **仅差科目** | **0.9224** |

最危险的是**科目**而非年份——0.9224 距 0.97 阈值只剩 0.05 余量。
而最初的 entity_key 只约束了公司与年份，
「2025年营业收入」与「2025年净利润」的 key 完全相同。科目维度是
实测之后补上的。架构文档里原本写「仅差年份相似度常在 0.97 以上」
是没有实测依据的，已改正。

**不缓存的情况**：拒答、空答、Agent 降级产生的答案。
把一次偶发失败固化下来，比不缓存糟得多。

## ✅ M6 · 模型路由（经评估后不做）

原计划按问题复杂度路由到不同档位的模型。**数据不支持这个优化**：

- 消融已证明 qwen-plus 相对 qwen-flash **无显著质量收益**
  （99.5% vs 98.4%，区间大幅重叠）而成本是 **4.3 倍**，
  所以不存在「难题换强模型」的依据
- 比 qwen-flash 更便宜且可用的档位不存在
- 现有成本结构里，多跳题 ¥0.004 是其余的两倍，但那来自 Agent 的
  多轮调用，换模型解决不了

按决策阶梯：**能用数据证明无收益的优化，不要只因为「架构里写了」就实现**。
真正有效的成本手段是缓存（降 83%）与宽截断配便宜模型。

## ✅ P1-7 · 汇总表召回（已改为结构化召回）

**原做法**：往关键词查询里拼表名「主要会计数据和财务指标」。
两个毛病：表名各家写法不同（上交所带「近三年」，深交所不带），
写死一种只覆盖一半公司——海康威视因此一直召回不到；
而且本质仍是和词频赛跑，而这张表每个科目只出现一次，天生吃亏。

**现做法**：解析阶段识别出这张表并打上 `chunk_type="table_summary"`
（判据是「标题含主要会计数据/主要财务数据」且「表内并列两个以上年份」，
不绑定任何一种措辞），检索时按标签直接点名取回并前置。
rag 与 agent 两条分支都已接入。

**前置是必要的**：它是往年数据唯一的权威来源，排在后面会被 top_n 截断扔掉，
那正是原来失败的方式。给它 0.02 的固定分值——高于相关度阈值 0.010
因而不会把整轮判成拒答，又低于真正命中的 RRF 分值，不挤掉更相关的块。

**原问题记录**

**现状**：实测该表在朴素查询下**任何公司、任何年份都进不了前 20**，
加上表名提示后稳定在第 2–6 名。原因是 BM25 按词频打分，
而这张表里每个科目只出现一次。

当前做法是查询年份早于报告年度时，往关键词查询里追加
「主要会计数据和财务指标」。这是硬编码的表名，有两个问题：

- 换一批公司若出现第三种叫法，又会只覆盖一部分（已经栽过一次：
  写死上交所措辞时深交所三家全不命中）
- 当年（本期）的问题不触发提示，汇总表同样进不了前 20，
  只是模型能从别处答对，属于侥幸

**处理计划**：改为结构化召回——给汇总表类块打标签（解析时已知其
heading 含「主要会计数据」），检索时按标签强制召回一条，
不再依赖关键词匹配。
