财报智能问答与分析服务

一个基于企业年报的检索增强问答与多步分析服务。用户以自然语言提问，系统从年报原文中检索证据并生成带引用的答案； 涉及跨公司对比、比率计算、趋势分析的问题，则由 Agent 自主编排工具完成。 项目的技术难点锚定在中文年报的表格数值问答——量纲混用、科目口径不一、表格跨页， 这些是英文财报场景遇不到、也最难被同类项目复制的问题。

01

服务定位与边界

1.1 一句话定义

FinCopilot 接收关于上市公司财务表现的自然语言问题，基于已入库的年报原文返回可溯源的答案； 当问题无法由单次检索回答时，自主调用检索、结构化查询、计算、绘图工具完成多步分析。

差异化定位

本项目真正稀缺的地方

「LangGraph + RAG + 财报 + RAGAS 评估」这个组合，开源社区已有相当数量的同类项目， 单靠「搭了一套带评估的 RAG 系统」不构成差异化。

本项目的立足点是更窄、更硬的一个问题：中文 A 股年报的表格数值问答，以及随之而来的单位归一与科目口径对齐。 英文 10-K 的项目遍地都是，但中文年报的表格结构显著更复杂——合并单元格多、量纲（元/万元/亿元）混用、 科目命名不统一——做的人少，难点真实、可量化、能讲出细节。

因此评估体系在本项目中的角色是证明工具而非主角：它用来证明「这个难题被解决到了什么程度」， 而不是作为卖点本身。

1.2 在做什么 / 不做什么

在范围内明确不做
A 股上市公司年报 / 季报 PDF 的解析与索引实时行情、盘中数据（只做静态报告 + 落库指标）
基于原文的事实问答，答案必须带页码级引用投资建议生成（触发即进人工确认，不自动输出）
表格类数值问答（营收构成、分季度数据）OCR 扫描件（仅支持文本层可提取的 PDF）
跨公司、跨年度对比与比率计算多租户与企业级权限体系（预留字段，不实现）
文档中无依据时明确拒答模型训练（仅一次 LoRA 微调小模型用于路由，属增强项）
全链路可观测、成本核算、离线评估移动端 App
边界的意义

「不做」清单和「做」清单同等重要。0→1 阶段的最大风险不是技术难度，是范围蔓延。 任何新想法先进 backlog，不进当前里程碑。

1.3 质量目标（可验收）

主指标——直接衡量答案对错，不依赖模型评判，是唯一的验收依据：

指标目标值验收方式
数值题准确率（单位归一后 ±0.5% 容差）≥ 80%评估集表格子集，确定性判定
事实题准确率≥ 88%评估集单跳子集，规则判定
拒答准确率（应拒答且拒答）≥ 90%评估集拒答子集
误答率（应拒答却作答）≤ 8%单独报告——最危险的失败模式
缓存误命中率≤ 0.5%按周抽检命中样本
指标抽取准确率≥ 95%人工核对 50 条；未达标则不开放 SQL 路径

辅助与工程指标——用于归因和容量规划，不单独作为验收门槛：

维度指标目标值验收方式
检索质量Recall@5≥ 85%评估集离线跑分
生成质量Faithfulness（忠实度）≥ 0.88RAGAS，仅用于定位生成环节问题
响应性能P95 首 token≤ 2.5 sLangfuse 统计
响应性能P95 完整回答（RAG 分支）≤ 8 sLangfuse 统计
成本单次问答平均成本≤ ¥0.01 已实测M2 实测 ¥0.0026–0.0033，目标据此收紧
成本语义缓存命中率≥ 25%Redis 命中统计
入库吞吐200 页年报端到端入库≤ 8 minWorker 任务耗时
成本：估算 ¥0.03 → 实测 ¥0.003

原估算担心「父子块还原 + top-5 父块」会把输入推到 6–10k token，实际 M2 实测 单次输入 3.0–4.1k token，成本 ¥0.0026–0.0033，比估算低约一个数量级。 原因是父块还原带了 token 预算裁剪与按 parent_uid 去重，上下文没有预想中膨胀。 目标据此收紧至 ¥0.01，保留约三倍余量给后续的重排与 Agent 多步调用。

这正是为什么估算值不能留在验收标准里：偏差方向和幅度都无法靠推理得出。 M5 接入 Agent 后成本结构会再变一次，届时需要重新实测。

使用场景全扫

设计前先把系统会被怎么用列全，包括异常路径。后续每条路径都要在测试矩阵中有对应用例。

2.1 正常路径

#路径触发分支关键设计点
P1管理员上传年报 PDF → 后台解析入库 → 查看状态变为 ready离线异步任务、状态机、幂等
P2提问单跳事实：「比亚迪 2024 年研发投入是多少」RAG向量召回 + 引用定位
P3提问表格数值：「列出宁德时代 2024 年分季度营收」RAG表格块不切断、父块还原
P4多轮追问：「那它的毛利率呢」（指代上一轮公司）RAG指代消解、会话记忆
P5跨公司对比：「对比茅台和五粮液近三年毛利率」Agent多次检索 + 计算 + 绘图
P6结构化查询：「营收超 500 亿且净利率大于 20% 的公司」AgentText2SQL + 结果校验
P7请求投资建议：「茅台现在值得买吗」Agent + HITL中断等待人工确认
P8重复/相似提问缓存精确缓存 + 语义缓存两级

2.2 异常与边界路径

#场景期望行为
E1问题在文档中无依据（如问 2026 年预测）明确拒答并说明原因，不编造
E2检索结果相关度全部低于阈值触发一次 query 改写重试；仍失败则拒答
E3问的公司尚未入库告知未收录，列出已收录公司范围
E4主模型超时 / 限流自动切备用 Provider，用户无感
E5Rerank 服务不可用跳过重排降级运行，响应标记 degraded
E6Agent 工具连续失败换工具或用已有信息作答，标注信息不完整
E7Agent 达到最大步数强制收敛作答，不无限循环
E8PDF 解析失败（加密 / 纯扫描件）状态置 failed 并记录原因，不阻塞其他文档
E9同一文档重复上传内容 hash 命中则跳过，不重复消耗 embedding
E10SSE 连接中途断开Checkpoint 已落库，重连可续；成本照常计入

4.2 进程形态：单体、双角色

同一份代码、同一个镜像，通过启动命令区分两种角色。在线请求与离线解析互不阻塞， 但部署单元仍然只有一个，避免个人项目背上微服务的运维成本。 

# 同一镜像，两种启动方式
API 角色    uvicorn app.main:app     处理在线问答，无重任务
Worker 角色 arq app.worker.Settings   消费文档解析队列，CPU 密集

任务投递：API 收到上传 → 写 documents 表(status=pending) → Redis 入队 → 立即返回
         Worker 消费 → 解析/分块/向量化 → 更新 status → API 侧轮询或 SSE 推送进度
这个选择的价值

面试被问「为什么不拆微服务」时，这是一个有依据的回答：负载特征不同（在线 IO 密集 / 离线 CPU 密集）所以要隔离， 但服务边界尚未稳定、团队只有一人，拆分带来的分布式复杂度大于收益。物理同构保留了后续独立扩缩的可能。

5.2 LangGraph 状态定义

class GraphState(TypedDict):
    # ── 会话上下文 ──
    conv_id: str
    trace_id: str
    messages: Annotated[list[BaseMessage], add_messages]

    # ── 查询处理 ──
    question: str                  原始提问
    rewritten: str | None          改写后（指代消解 / HyDE）
    route: Literal["chat","rag","agent"]

    # ── 检索结果 ──
    retrieved: list[RetrievedChunk]
    citations: list[Citation]
    relevance: float               grade 节点打分
    retry_count: int               改写重试次数，上限 1

    # ── Agent 执行 ──
    tool_calls: int                已执行步数
    tool_errors: int
    scratchpad: list[dict]

    # ── 输出 ──
    answer: str
    refused: bool
    refuse_reason: str | None
    needs_approval: bool           触发 interrupt()
    degraded: list[str]            降级项，如 ["rerank_skipped"]
    usage: TokenUsage

5.4 Provider 抽象层

百炼、DeepSeek、火山方舟、vLLM 全部提供 OpenAI 兼容端点。因此抽象层不是类继承体系，而是一张配置表加一个工厂函数—— 这是刻意的克制：能用配置解决的，不引入代码抽象。 

# configs/models.yaml
profiles:
  strong:      { provider: bailian,  model: qwen3-max,        price_in: 0.0024, price_out: 0.0096 }
  light:       { provider: deepseek, model: deepseek-chat,    price_in: 0.0005, price_out: 0.0015 }
  router:      { provider: vllm,     model: qwen3-1.7b-lora,  price_in: 0,      price_out: 0 }
  embed:       { provider: bailian,  model: text-embedding-v4, dim: 1024 }
  rerank:      { provider: bailian,  model: gte-rerank-v2 }
fallback:
  strong: [light]          主模型不可用时的降级顺序

06

核心流程

6.1 离线入库

  1. 接收与去重 计算文件 SHA-256，命中 documents.content_hash 则直接返回已有 doc_id，不重复处理。写入记录，状态 pending，投递队列。
  2. 解析 PDF → 结构化 Markdown，保留标题层级与表格边界。表格单独提取为独立单元，不与正文混排。 三类表格必须专门处理：跨页表格需回补表头、合并单元格需展开、表头单位需下沉到每行。状态 parsing。
  3. 分块 按配置的策略切分（heading 为默认）。每块生成父子两级：父块保留完整小节，子块为检索粒度。每块拼接标题路径前缀，使孤立块也具备上下文。
  4. 元数据抽取（含量纲与口径） 基础项：公司代码、报告年度、章节路径、页码区间、块类型。 表格块额外抽取四项结构化元数据：unit（元/万元/亿元）、currency、period（报告期）、statement_type（报表类型）。 这些既是检索过滤条件，也是生成阶段防止单位与口径错配的依据。
  5. 向量化 子块批量送 embedding（批大小 64，失败指数退避重试 3 次）。状态 embedding。
  6. 双写 向量 + 标量字段写 Milvus；原文与结构关系写 PostgreSQL。先写 PG 再写 Milvus，失败时以 PG 为准做补偿重建。
  7. 指标抽取与质量校验 从表格块提取标准财务指标入 financial_metrics，供 Text2SQL 使用。 每条记录必须保留来源回链（doc_id + page + chunk_uid）与抽取置信度； 并与 AKShare 的同期公开指标做交叉校验，不一致的记录标记为待核。抽取失败不影响文档可用。
  8. 完成 状态置 ready，记录块数、token 数、耗时、embedding 成本。
表格才是真正的难点

「表格不切断」只解决了问题的一小部分。中文年报数值问答的实际瓶颈是另外三个，且都不是分块能解决的：

① 量纲混用——同一份年报中「元 / 万元 / 亿元」并存，常见做法是表头标单位、数据行不标， 分块后单位信息与数据分离，模型直接读出错误量级。
② 科目口径——「营业收入」与「营业总收入」是两个科目，「净利润」与「归属于母公司股东的净利润」也不同。 检索命中了正确的表却取错行，答案照样是错的。
③ 跨页与合并单元格——长表跨页后表头丢失，合并单元格解析后行列错位。

应对方式是把单位与口径结构化为元数据而非留在文本里（步骤 4），并在生成阶段强制模型声明单位与科目全称（§6.2 步骤 9）。 这一块做扎实，是本项目最能讲出细节、也最难被同类项目复制的部分——英文 10-K 场景基本遇不到这些问题。

结构化指标是一个静默错误源

从年报表格抽取指标入库，抽取过程本身会出错。而错误的结构化数据一旦走 Text2SQL 路径， 会产出看起来精确的错误数字——比检索幻觉更难察觉，因为它带着数据库查询的权威外观。

因此三重防护：来源回链（每条指标可定位到原文页）、外部交叉校验（与 AKShare 公开指标比对）、 上线前抽样验证（人工核对 50 条，测出抽取准确率并写入文档）。 抽取准确率低于 95% 时，不开放 SQL 查询路径——宁可少一条能力，不可给出权威的错误答案。

增量更新

文档内容变化时对比 hash：整体不变跳过；变化则按块级 hash 比对，只重算变动块，其余向量保留。 这一步在 0→1 阶段可以简化为「全量重建」，但接口要留好，这是 M6 的优化项。

6.2 在线问答（RAG 分支）

  1. 入口护栏限流（每用户每分钟 N 次）、长度截断、提示注入模式检测。
  2. 缓存查询（含实体硬约束） 一级：问题归一化后 hash 精确匹配。二级：先抽取实体三元组（公司代码集合、报告期集合、指标类型）， 三元组必须完全一致，才允许在 query_cache 中做向量相似度匹配（阈值 0.97）。命中则标记 cached 返回。
  3. 查询改写 多轮场景做指代消解（「它」→ 具体公司）；同时抽取结构化过滤条件（公司、年份）供检索使用。HyDE 作为可开关项参与消融实验。
  4. 路由（保守兜底） 轻量模型结构化输出判定 chat / rag / agent，同时输出置信度。 置信度低于阈值时默认走 agent——agent 能力是 rag 的超集，判错的代价只是多花成本，反向判错则会直接答错。
  5. 混合检索 Milvus 同时执行 dense 向量检索与 sparse（BM25）检索，RRF 融合，各取 top-20。标量条件下推到检索层，不做后置过滤。
  6. 重排Rerank 模型对 40 个候选打分，取 top-5。服务不可用时跳过，标记 degraded。
  7. 父块还原（去重 + 预算裁剪） 将命中的子块替换为其父块。多个子块常同属一个父块，必须按 parent_uid 去重，否则上下文重复、成本翻倍。 去重后按 token 预算截断，保留重排分数最高的父块；表格类父块优先保留完整，不做中途截断。
  8. 相关度判定 低于阈值：触发一次改写重试；仍低于阈值则进入拒答分支，明确告知「已检索的文档中没有找到依据」。
  9. 带引用生成 Prompt 强制要求每个事实性陈述标注来源编号，数值类回答必须同时声明单位与科目全称（如「营业总收入，单位：人民币亿元」）。 流式输出，先推 citation 事件再推正文 token。
  10. 核验与落库 校验引用编号均存在且未越界；写缓存；上报 Langfuse（各阶段耗时、token、成本）。
为什么语义缓存必须加实体硬约束

在财报领域，下面两个问题的向量相似度几乎必然超过 0.96：

"茅台 2023 年营业收入是多少" 与 "茅台 2024 年营业收入是多少"

仅差一个数字，嵌入模型无法有效区分。同类情形还有「茅台 vs 五粮液」「营业收入 vs 营业总收入」。 一旦错误命中，系统会返回一个精确、自信且完全错误的数字，并且毫无察觉—— 这比生成式幻觉危险得多，因为链路追踪也看不出异常。

因此缓存键的结构是 (公司集合, 报告期集合, 指标类型) 必须精确相等， 向量相似度只用于匹配问法差异。实体不一致即判定未命中，无论相似度多高。 上线后需按周抽检缓存命中样本，统计误命中率并纳入指标体系。

6.4 人工确认（HITL）

当 verify 节点识别出输出属于投资建议类内容时，置 needs_approval=true 并调用 interrupt()。 图状态由 Checkpointer 落库，SSE 推送 interrupt 事件，前端展示待确认内容与免责说明。 用户确认后以 Command(resume=...) 恢复执行；拒绝则转为中性信息陈述。

为什么这个场景值得做

HITL 常被做成硬凑的演示功能。但金融场景下「AI 不得直接输出投资建议」是真实合规要求， 中断点的存在有业务理由而非技术炫技——这使它成为一个能讲清楚的设计，而不是一个可有可无的开关。

为什么是 320 而不是 120

原定 120 条的设计前提是「全靠手工标注」，这个约束已随 FinGLM 标注池的引入而消失。 而 120 条存在实打实的统计功效问题：拒答子集仅 20 条时，指标粒度是 5 个百分点， 单条题目的翻转就等于 5 个点的波动；单跳 60 条时，Recall@5 从 85% 到 89% 只相当于 2.4 条题的差别， 不具备统计显著性。

实验记录表要承载 8 行以上的对比数据，若每行的误差带都大于行间差异，整张表在方法上不成立。 因此所有指标必须以 bootstrap 95% 置信区间报告，而非点估计（见 §12.4）。

12.2 指标：主指标与辅助指标

一个必须纠正的设计错误

Recall、Faithfulness、Answer Relevancy 全部是代理指标。 Faithfulness 高只说明「模型忠实复述了检索结果」——若检索回来的是错误段落，模型忠实地引用它， Faithfulness 依然很高，而答案是错的。把代理指标当验收标准，会系统性地高估系统质量。

财报数值问答恰恰具有唯一正确答案，这是本选题最大的优势。因此引入端到端答案正确率作为主指标， RAGAS 系列降为辅助指标。

主指标 — 端到端答案正确率

指标定义判定方式
数值准确率数值类问题答对的比例单位归一后按 ±0.5% 容差匹配；单位或科目错即判错
事实准确率非数值事实类问题答对的比例关键实体与结论的精确匹配，人工制定判定规则
拒答准确率应拒答且实际拒答 ÷ 应拒答总数确定性判定，无需模型参与
误答率应拒答却给出了答案的比例与拒答准确率互补，但单独报告——这是最危险的失败模式

主指标的三个优势：不依赖 LLM-as-judge，因此没有评判噪声；成本近似为零；对外表述无需解释—— 「数值题准确率 82%」任何人都懂，「Faithfulness 0.86」需要解释半天。 更关键的是，它能直接暴露单位换算、科目错配这类真实缺陷，而 Faithfulness 对此完全不敏感。

12.3 实验设计

顺序叠加的陷阱

逐项累加式消融（exp01 → exp08）存在路径依赖：分块策略的最优选择， 是在「无重排」条件下得出的，未必在「有重排」条件下依然成立——重排能挽回一部分召回损失， 可能把分块策略的差异抹平。顺序叠加只能得到一条路径上的局部结果，不足以支撑「A 策略优于 B 策略」这类普遍结论。

13.2 关键分歧点

① 用框架，还是自己实现检索链

结论是能用框架就用框架。技术深度不体现在实现层——没有人会因为用了 LangChain 扣分， 但会因为说不清框架内部做了什么扣分。深度来自三件事：组件选型的依据、参数调优的数据、线上问题的归因。 省下的实现时间应当投入 Agent 编排与评估体系，那里的概念密度和产出价值都高得多。

配套方法

用框架而不失深度的做法是看 trace 而非读源码。Langfuse 中能看到框架实际发出的每条 prompt、 检索返回的原文、每步的 token 消耗，隐式行为一览无余。再对每个默认值追问一次为什么—— chunk_size 为何是 1024、top_k 为何是 2、阈值依据什么定——每个默认值都是一次实验机会。

② LangChain 还是 LlamaIndex

维度LangChainLlamaIndex
RAG 抽象清晰度中高（Document → Node → Index → Retriever）
父子块与表格的开箱能力需组装内置更完善
与 LangGraph 集成同生态，无缝需适配
岗位要求出现频率显著更高中

选 LangChain 作主线是生态一致性与覆盖面的考量。但 LlamaIndex 不是弃选，而是作为对照组实现同一套检索链， 跑同一评估集出对比数据（实验 exp08）。这样「为什么选 LangChain」有数据可答，而不是只能回答「因为大家都用」。

③ LangGraph 还是 CrewAI / AutoGen

LangGraph 的状态机模型能精确表达本项目需要的三件事：条件路由、步数护栏、中断恢复。 CrewAI 与 AutoGen 侧重多智能体角色协作，抽象层级更高但可控性更弱，且 0→1 阶段不含多智能体。 多引入一个 Agent 框架不会带来增量的技术信号，只会扩大维护面。

④ arq 还是 Celery

Celery 功能更全但配置繁重，其 asyncio 支持也仍不理想。arq 基于 asyncio 与 Redis，与 FastAPI 共用同一并发模型，配置约十行。 本项目任务类型单一（文档解析），用不上 Celery 的路由、优先级与工作流编排能力。按决策阶梯，够用即止。

⑤ Chainlit 还是自建前端

前端不是考察维度，但演示效果直接影响第一印象。Chainlit 用 Python 即可实现流式对话、引用卡片、 Agent 步骤展示与人工确认交互，成本极低。后期若需要更强的品牌感再替换为独立前端—— 接口协议（§8.2）已与前端实现解耦，替换不影响后端。

⑥ LoRA 微调 + vLLM 自托管：一个诚实的说明

这一项的投入产出比是负的

路由与查询改写任务，用规则前置过滤加轻量模型 API 已经完全够用。自己微调一个小模型再自托管推理， 需要租 GPU、准备训练数据、调参、部署服务——时间与成本远大于它带来的工程收益。

它留在计划里的唯一理由是：LoRA 与 vLLM 在岗位要求中出现频率不低，纯应用型项目天然覆盖不到。 因此它被明确放在 v1.1 而非 0→1 范围，且在文档中直说其性质。

主动说明这一判断，比假装它有技术必要性更有价值。 面试时能讲清「我知道这个东西在我的场景里 ROI 为负，我做它是为了补技能覆盖， 但如果是生产系统我不会这么选」——这是工程判断力的体现，远胜于把它包装成核心技术。

14.1 三条选型原则

原则展开
供应商数量是第一成本项 每多接一个平台，就多一套注册、鉴权、配额规则、故障排查路径。目标是把账号数压到 3 个：一个模型平台、一个应用托管平台、一个可观测平台。
付费买省事，不拼免费额度 用多个免费层拼出的系统，任何一处额度耗尽整条链路就断，而且排查时分不清是代码问题还是配额问题——这是项目烂尾的典型路径。凡是会成为瓶颈的服务，直接付费。
按信号价值分层投入 模型平台、向量库、框架的选择会被反复追问，必须对齐行业主流；托管平台几乎不会被问，选最省配置时间的即可。把精力花在会被检验的地方。
免费层的正确用法

免费层不是一律不能用，判断标准是两条：额度相对实际用量有多少倍冗余，以及用完之后是降级还是硬断。 冗余在十倍以上、且超额只是排队或降速的，可以放心用；冗余不足两倍、超额即拒绝服务的，一律换付费。

ADR-011一切中间件用托管服务，不自建自建 Milvus / Redis / Langfuse 需持续运维，注意力应留给检索与 Agent。代价：月度固定支出，且受平台可用性约束。
ADR-012托管平台选 Zeabur 而非国内大厂云部署平台不具备简历信号价值，选型只看配置负担；Zeabur 国内直连、数据库一键接入且连接串自动注入。代价：平台小众，极端情况需迁移——但应用已容器化，迁移成本可控。
ADR-013语义缓存必须叠加实体硬约束（公司 + 年份 + 科目）纯相似度匹配会返回精确但错误的数字且无法察觉。M6 实测各类单一差异的余弦相似度（text-embedding-v4）：仅差公司 0.5824，仅差年份 0.86–0.87，仅差科目 0.9224——最危险的是科目而非年份，它距 0.97 阈值只剩 0.05 余量。本条最初只约束公司与年份，科目维度是实测之后补上的；设计阶段写的「仅差年份相似度常在 0.97 以上」并无实测依据，已更正。代价：命中率下降，实现复杂度增加。可信度优先于命中率。
ADR-014主指标用端到端答案正确率，RAGAS 降为辅助Faithfulness 等均为代理指标——模型可以忠实地复述错误的检索结果。财报数值有唯一答案，可做确定性判定，无评判噪声且零成本。代价：需为每类题目制定判定规则。
ADR-015评估集 320 条，指标以 bootstrap 95% CI 报告120 条时子集仅 20–60 条，单题翻转即造成数个百分点波动，行间差异被噪声淹没，实验记录表在方法上不成立。代价：复核工作量增加，评估耗时与成本上升。
ADR-016表格的量纲与科目口径结构化为元数据中文年报量纲混用、科目命名不统一，是数值题出错的首要原因，留在文本里模型无法可靠识别。代价：解析链路复杂度显著上升。这是本项目差异化的核心投入。
ADR-017消融分三阶段：顺序 + 交叉 + 逆向纯顺序叠加存在路径依赖，无法支撑「A 优于 B」的普遍结论。交叉验因子独立性，逆向算边际贡献。代价：实验次数增加约一倍。
ADR-018指标抽取准确率不达 95% 则不开放 SQL 路径错误的结构化数据会产出带有数据库权威外观的错误数字，比检索幻觉更难察觉。代价：可能损失一条能力线。
ADR-019报表口径（合并/母公司）作为跨页继承的标签写入块正文三大报表每张横跨两三页，标题只印在起始页，续页解析出的块与另一口径的块逐字相同——实测茅台 p64（合并现金流量表）与 p66（母公司现金流量表）的块完全无法区分，而两者经营活动现金流净额相差近一倍（615 亿 vs 326 亿）。与量纲同属一类问题，解法一致：标题识别 + 跨页继承，章节变更或超过 4 页即失效。代价：解析链路再增一层状态。
ADR-020检索查询按「区分度」构成：过滤字段不进文本，区分字段必须进公司名已由 company_code 标量过滤处理，过滤后候选集内每页都含该词，区分度为零却稀释 BM25 权重——实测带公司名时 p6 摘要表进不了前 20，去掉后排第 1。反之年份明写在表格列头（| 2025年 | 2024年 | 2023年 |），必须进检索文本；仅作标量过滤无效，因为 report_year 是文档年度，一份年报同时匹配三个查询年份。代价：查询构造需要知道哪些字段已被过滤。
ADR-021评估集的自动生成底稿必须用独立代码路径对账底稿由解析器抽取，而被评估系统用的是同一个解析器：解析器读错列时，标准答案与系统回答会一起错，评估全绿而结论是假的。每条抽取值回到原始页面文本（get_text，不经 find_tables）核对一次，可独立证伪「这个数不在这一页上」。代价：无法完全自动化，年份归属仍需人工看列头。
ADR-022三年并列表在解析阶段按年份展开成明细行「主要会计数据」表把三年并排列出，要答对往年数据模型必须先数清第几列对应哪一年，实测 flash 与 plus 都会数错（问 2024 年给出 2025 年的数），往提示词里加两轮规则都压不住。改为解析时额外输出「【按年份】营业收入：2025年=…；2024年=…；2023年=…」，模型只需字符串匹配。这是继量纲（ADR-016）、报表口径（ADR-019）之后第三次应用同一判断：程序能确定做出来的结构，不要留给模型推断——提示词规则是概率性的，解析结构是确定性的。代价：只在能确定对齐时输出（列头至少两个年份、排除增减率列、年份不得重复），对不齐则整段放弃，覆盖率换正确率。

19.1 三个长度的项目自述

30 秒版（自我介绍时用）

「我做了一个基于 A 股上市公司年报的智能问答系统。用户用自然语言提问，系统从年报原文里找到依据、 给出带页码引用的答案，答不了的会自己调工具去查数据、做计算、出图表。 难点在中文年报的表格——量纲混用、科目名不统一、表格还跨页， 我用一套结构化元数据的方案把数值题准确率从 X% 提到了 Y%。」

2 分钟版（追问"详细说说"时用）

在 30 秒版基础上补三段，每段一句话打底、一个数字收尾：

  1. 系统是怎么搭的——离线把年报解析、分块、向量化入库；在线走路由，简单问题走检索，复杂问题走 Agent 多步编排。
  2. 怎么知道它好不好——先建了 320 条评估集，跑出基线，之后每做一次优化就跑一次，记录一行数据。指标带置信区间，不是拍脑袋的数字。
  3. 做了哪些取舍——举一个主动砍掉的东西（如逆向消融发现某组件边际收益不足 1 个点却增加 20% 成本）。

19.2 高频追问与回答要点

问题回答要点依据
你的检索不准，怎么解决的？ 先定位是召回问题还是生成问题（看 Recall 与 Faithfulness 哪个低）→ 再按混合检索、重排、改写逐项验证 → 每步有数据。不要直接答「加了 rerank」，要展示定位过程§12.2
为什么这样分块？ 试了固定长度、递归、按标题三种并对比；表格场景下固定长度会把表头和数据行切开，导致单位丢失§6.1 §12.3
怎么评估效果？ 这是最能拉开差距的一题。主指标是端到端答案正确率（确定性判定），RAGAS 只作辅助归因；评估集 320 条分四类；指标报 bootstrap 95% 置信区间§12
幻觉怎么防？ 四层：强制引用、相关度阈值拒答、引用编号核验、评估集里专门的拒答子集与误答率指标§6.2 §1.3
Agent 怎么保证不跑飞？ 步数上限、工具白名单、参数校验、错误次数上限、单会话成本预算；触顶时强制收敛作答而非无限循环§6.3
成本怎么控制？ 两级缓存 + 模型路由 + 空检索短路 + 上下文预算裁剪；有具体下降幅度。要主动提缓存误命中的风险和防护§10.2
线上出问题怎么排查？ Langfuse 全链路 trace，记录了 retrieved_uids，可以倒查「这个错误答案当时检索回了什么」——没有这个字段，bad case 无法归因§10.3
为什么用 Milvus 不用 pgvector？ 原生混合检索与标量过滤下推；本地开发保留 pgvector 作降级方案。要说出代价：多一个外部依赖ADR-002
为什么 LangChain 不是 LlamaIndex？ 两个都实测过（exp09 对照组）：LlamaIndex 分块开箱效果更好，LangChain 与 LangGraph 集成更顺。有数据，不是「大家都用」§13.2
用了框架，你自己做了什么？ 选型依据、参数调优、问题归因。举例：在 trace 里发现框架默认的查询改写在中文短问句上引入噪声，因此关闭换成自定义 prompt§13.2
这个项目最难的是什么？ 中文年报表格的量纲与科目口径对齐。举一个具体 bad case，讲清现象、定位、方案、数据§6.1
重做的话你会改什么？ 诚实回答。例如：评估集应该一开始就做到 300 条以上，120 条的统计功效不足；或 LoRA 那块 ROI 为负，生产系统不会这么选§13.2 ⑥

一句话怎么讲出处
换评估集掉了 22.6 个点 v1（61 题 / 2 家公司）上连续两次满分，同一套代码跑 v2（182 题 / 12 家）只有 74.7%。 那 22.6 点就是对着 61 道题调了六轮提示词的过拟合代价。当时就拒绝把满分写成「准确率 100%」， 写进了待办清单——这一点比分数本身更值得讲benchmarks

两张报表解析出的块逐字相同 经营活动现金流同比算出 -11.43%，正确是 -33.46%。打印两个候选块的原文， 发现合并现金流量表与母公司现金流量表的块一个字都不差——报表标题只印在起始页， 续页没有。与「元/千元」是同一类问题，解法也一样：跨页继承。 两者数值差近一倍（615 亿 vs 326 亿）7.3 / ADR-019
最该检索到的表从未进过前 20 四家公司 × 两个年份 × 两种查询拉成一张表：「主要会计数据」汇总表在朴素查询下 一次都没进过前 20，加上表名提示后稳定在第 2–6 名。 原因是 BM25 按词频打分，而这张表里「营业收入」只出现一次。 信息密度最高的内容在词频检索里天然是弱者。 指标还有 97%，只是因为模型从别处也能答对当年的数7.16

19.3 技术叙事模板

每个技术点都应该能用这个结构讲满两分钟。开发过程中每遇到一个 bad case 就按此模板记一条，到收尾时素材自然齐备。

① 现象   涉及表格的数值题准确率明显偏低，只有 45%

② 定位   抽 20 个 bad case 看 trace，发现检索回的片段里有数字、没有单位——
          表头写着"单位：万元"，但分块时表头与数据行被切开了

③ 假设   不是召回问题（Recall 正常），是分块策略导致量纲信息丢失

④ 方案   表格整块不切分 + 把 unit / statement_type / period 抽为结构化元数据
          随块返回，生成阶段强制模型声明单位与科目全称

⑤ 数据   该类问题准确率 45% → 82%，总体数值准确率 +11 个点

⑥ 取舍   块变大，输入 token 涨了约 15%，单次成本上升；
          用语义缓存把这部分抵消回来，净成本基本持平
为什么这个结构有效

它同时展示了五种能力：发现问题（有监控）、定位问题（会看 trace）、 形成假设（不瞎试）、量化效果（有数据）、权衡代价（懂工程）。 单纯罗列技术名词只能展示第零种。

19.5 不要说的话

不要说原因与替代说法
「我用 RAG 做了个知识库」信息量为零。替代：说清难点是什么、用什么方法、提升了多少
「部署在生产环境，有真实用户」夸大事实，一问细节就露馅。如实说是个人项目、有公开 demo
「我自己实现了混合检索算法」框架已提供的东西不要说成自研。替代：说你如何选型、如何调参、如何验证

「这个我了解过」模糊表述会引来更深的追问。不会就直说不会，然后说你会怎么查

20.1 检索增强（RAG）相关

术语大白话解释
RAG
检索增强生成		让大模型回答问题前，先去资料库里"翻书"找到相关段落，再基于这些段落回答。好处是答案有依据、可溯源，且换资料不用重新训练模型
Embedding
向量 / 嵌入		把一段文字转换成一串数字（本项目是 1024 个）。意思相近的文字，数字也相近。这样"找相似段落"就变成了"找相近数字"
向量数据库专门存这些数字串并快速找出最相近几条的数据库。本项目用 Milvus
Chunking
分块		把长文档切成小段再存。切得太大检索不精准，太小又会丢失上下文——切法本身就是一门手艺
父子块
small-to-big		同一段内容存两份：小块用来精准检索，大块用来喂给模型。兼顾"找得准"和"看得全"
召回 / Recall@K该找到的资料，有没有出现在返回的前 K 条里。Recall@5 = 85% 意思是 100 次里有 85 次正确资料出现在前 5 条中
BM25传统的关键词匹配算法。和向量检索互补：向量懂语义但可能漏掉精确的专有名词，BM25 正好相反
混合检索同时用向量和 BM25 检索，再把两份结果融合排序（本项目用 RRF 算法融合）
Rerank
重排		检索出 40 条候选后，用一个更精细（也更慢）的模型重新打分，挑出最好的 5 条。相当于"粗筛 + 精选"两道工序
查询改写把用户的原话改成更适合检索的形式。比如多轮对话里「它的毛利率呢」要先还原成「贵州茅台的毛利率」，这一步叫指代消解
HyDE一种改写技巧：先让模型"假装"写一个答案，再用这个假答案去检索。因为答案和资料的措辞更接近，有时比用问题检索更准
幻觉模型一本正经地编造事实。RAG 能大幅缓解但无法根除，所以还需要引用核验和拒答机制

20.2 智能体（Agent）相关

术语大白话解释
Agent
智能体		能自己决定"下一步干什么"的模型程序。比如为了回答对比问题，它自己决定先查 A 公司、再查 B 公司、然后算比率、最后画图
Function Calling
工具调用		模型不直接回答，而是输出一个"我要调用某个函数、参数是这些"的结构化请求，程序执行后把结果给它。这是 Agent 能干活的基础
ReAct一种 Agent 工作模式：思考 → 行动 → 观察结果 → 再思考，循环直到得出答案
LangGraph把 Agent 的执行流程画成一张"状态图"的框架：每个节点是一步操作，边是流转条件。好处是流程可控、可中断、可恢复
Checkpoint把执行到一半的状态存进数据库。断线或崩溃后能从中断处继续，不用从头再来
HITL
人工确认		Human-in-the-loop。关键操作前暂停，等人点头再继续。本项目用在"投资建议"类输出上，因为合规上 AI 不能直接给投资建议
护栏
Guardrail		防止 Agent 失控的各种限制：最多走几步、只能用哪些工具、花多少钱就停
Text2SQL把自然语言问题翻译成数据库查询语句。方便但危险——必须限制成只读、限制可查的表
MCP一种让工具能被不同 AI 应用通用调用的协议标准，相当于工具界的 USB 接口

20.3 评估相关

术语大白话解释
评估集一批事先准备好标准答案的题目。每次改动后都用同一批题重跑，才能知道是变好还是变坏
基线
Baseline		优化之前的初始成绩。没有基线，后面所有"提升了多少"都无从谈起——所以评估集必须先于优化建立
消融实验
Ablation		一次只改一个地方，看指标变化多少，从而判断每个改动各自贡献了多少。类似控制变量法
代理指标不能直接衡量目标、只能间接反映的指标。比如"忠实度"高不代表答案对，只代表模型老实复述了检索结果
LLM-as-judge用大模型给另一个大模型的输出打分。方便但有噪声且花钱，所以本项目只把它当辅助手段
RAGAS一个专门评估 RAG 系统的开源工具，提供忠实度、答案相关性等指标
Faithfulness
忠实度		答案里的每句话，是不是都能在检索到的资料里找到依据
置信区间
Bootstrap CI		题目数量有限时，测出的准确率本身带误差。置信区间就是给出"真实值大概率落在哪个范围内"。两组数据的区间重叠，就不能说谁更好
统计功效样本量够不够支撑结论。20 道题时一道题的对错就是 5 个百分点，这种波动会淹没真实差异

20.4 工程相关

术语大白话解释
Token模型处理文字的最小单位，中文大致一个字一个 token。模型按 token 数收费，所以 token 就是钱
Prompt发给模型的指令文本。写法直接决定输出质量，所以"prompt 工程"是一项真实技能
Trace
链路追踪		把一次请求经过的每一步、每步的耗时和花费都记录下来。出问题时能倒查，是排障的唯一依据
SSE
流式输出		答案边生成边推送给用户，不用等全部写完。体验上等同于打字机效果
语义缓存意思相近的问题直接返回上次的答案，省钱省时间。但相近的判断必须严格，否则会返回错误答案（见 §6.2）
降级某个环节坏了时，用次优方案继续服务而不是整个挂掉。比如重排服务挂了就跳过重排
幂等同样的操作重复执行，结果不变。比如同一份文档重复上传不会重复入库
LoRA 微调不改动原模型，只训练一小部分附加参数，让模型适应特定任务。比全量训练便宜得多
vLLM一个高效的模型推理服务框架，用于自己部署模型对外提供 API
ADR
架构决策记录		把"为什么做这个选择、代价是什么"写下来存档。见 §17
