0A零基础术语表

看代码之前先把这十四个词弄清楚。每条都标了它在本项目的哪个文件里。

RAG检索增强生成
先去资料库里把相关内容找出来，再连同问题一起交给大模型回答。好处是模型答的是你的资料、能标出处；坏处是找错了就答错。整个项目就是一套 RAG 系统
块chunk
资料不能整本丢给模型（装不下也不精准），要切成几百字的小片。每一片就是一个"块"。切得好不好，直接决定检索准不准。app/rag/chunker.py
父子块small-to-big
一个两难：块小了检索准但上下文不全，块大了上下文全但检索不准。解法是切两层——用小块（子块）去匹配，命中后换成它所属的大块（父块）送给模型。chunker.py 的 level 字段；retrievers.py:313 expand_parents
Embedding向量化
把一段文字变成一串数字（本项目是 1024 个），意思相近的文字对应的数字串也相近。这样"找相关内容"就变成了"找数字串距离最近的"。模型 text-embedding-v4，调用在 indexer.py:92
向量数据库Milvus
专门存这些数字串、并能在百万条里毫秒级找出最近邻的数据库。本项目用 Milvus 3.x。app/store/milvus_schema.py
HNSW
向量库里最常用的索引结构。它找的是"足够近"而不是"绝对最近"——用一点精度换几百倍速度。M 和 efSearch 两个参数控制这个取舍。configs/settings.yaml 的 milvus.index
BM25稀疏检索 / 关键词检索
传统的关键词匹配打分算法。它不懂语义，但对专有名词、数字、生僻词特别准——正好补向量检索的短板。Milvus 内置 Function，从 content 自动生成 sparse_vector
混合检索hybrid
向量和 BM25 各查一遍，再把两份结果合成一份。本项目两路各取 20 条。retrievers.py:214 retrieve
RRF倒数排名融合
合并两份排名的办法：不比较分数（两套分数没有可比性），只看名次，每条的得分是 1/(k+名次) 之和。本项目 k=60。pymilvus 的 RRFRanker(60)
重排rerank
检索完再用一个更贵但更准的模型把结果重新排序。业界默认"加了总没坏处"——本项目实测掉 6.1 点，已关闭，原因见第七节。app/providers/reranker.py；开关在实验配置里
Agent智能体
让模型自己决定"下一步该调用哪个工具"，循环多次直到能回答。本项目用它处理需要多次查、或需要计算的问题。app/graph/nodes/agent.py
ReAct
Agent 最常见的写法：思考 → 调用工具 → 看结果 → 再思考，循环。必须配护栏（最多几步、失败几次停、花多少钱停），否则会无限转圈烧钱。agent.py:112 agent_node，护栏阈值在实验配置 agent 段
消融实验ablation
一次只改一个因素，跑同一套题，看指标变化多少。这是判断"某个优化到底有没有用"的唯一可靠办法。configs/experiments/*.yaml，一个文件一组实验
置信区间 / 留出集
题目数量有限时，正确率本身带随机性。置信区间给出"真实水平大概在哪个范围"；两组区间重叠就不能说有提升。留出集是一批开发期间完全没碰过的题，用来检验你是不是只是把参数调得贴合了旧题目。eval/metrics.py:304 bootstrap_ci

01一、这个项目是什么

给定一批 A 股上市公司的年报 PDF，回答关于其中财务数据的问题——每个数字标注来源页码，查不到就明说查不到。

它和普通 RAG demo 的区别，在于防的是一类特定失败：看起来完全正确的错误答案。数字格式对、引用齐全、单位也写了，但答的是另一年、另一个口径、另一家公司——用户从输出上完全发现不了。这类错误比胡编乱造危险得多。

三个来源，全是中文年报特有的：

难点具体表现后果怎么解的
量纲混用茅台用「元」，宁德时代用「千元」，招行用「百万元」跨公司比较差 1000 倍解析时把 【单位：千元】 写进块的正文
报表口径合并报表 ≠ 母公司报表；营业收入 ≠ 营业总收入数值差近一倍，且两张表解析出来逐字相同口径标题跨页继承，同样写进正文
表格结构跨页、合并单元格、三年并列、无边框年份张冠李戴坐标重建兜底；三年表展开成 【按年份】 行
贯穿全项目的一条原则

程序能确定地做出来的结构，不要留给模型去推断。单位、口径、年份归属都属于这类——解析阶段就能确定，所以全部在解析阶段写死进文本，而不是指望模型生成时猜对。读代码时你会看到这条原则反复出现，它是理解大部分设计选择的钥匙。

03三、跑起来

全程约 1 小时，其中入库最花时间。每一步都有验收标准，不要跳过验收直接做下一步。

前置

  • Python 3.11+（requires-python = ">=3.11"）
  • Podman 或 Docker，用来起 PostgreSQL / Redis / Milvus
  • 一个阿里云百炼的 API Key（DASHSCOPE_API_KEY）。LLM、Embedding、Rerank 都走它。DeepSeek 的 Key 可以留空
  • 磁盘：Milvus 全家桶 + 年报 PDF，预留 5–10 GB

第 1 步 · 起存储

podman compose up -d        # 或 docker compose up -d

起五个容器：postgres(5432)、redis(6379)、etcd、minio、milvus(19530 / 9091)。后两个是 Milvus 的依赖，不用管。

验收：podman ps 看到五个容器都是 healthy。Milvus 首次启动要 1–2 分钟，没 healthy 就等。

docker-compose.yml 里还有 api / worker / ui 三个服务，挂在 full profile 下，up -d 不会启动它们。本地开发时代码在宿主机跑，这是对的。

第 2 步 · 装依赖、配环境变量

python -m venv .venv
.venv\Scripts\activate          # Windows；macOS/Linux 用 source .venv/bin/activate
pip install -e ".[dev]"
copy .env.example .env          # 然后编辑 .env，填 DASHSCOPE_API_KEY

.env 的全部变量：

变量说明必填
DASHSCOPE_API_KEY阿里百炼，LLM / Embedding / Rerank 都用它是
DEEPSEEK_API_KEY备用厂商，用于降级和评判模型否
POSTGRES_DSN默认值对应 compose，直接用有默认
REDIS_URL同上有默认
MILVUS_URI同上有默认
LANGFUSE_*可观测平台，留空则静默跳过上报否
EXP_ID默认用哪组实验配置，如 exp00_debug有默认
LOG_LEVEL排查问题时改成 DEBUG，能看到检索细节有默认
Windows 必看

连接串里必须用 127.0.0.1 而不是 localhost。Windows 上 localhost 优先解析到 IPv6 的 ::1，而容器端口转发只监听 IPv4——用 localhost 会一直挂起到超时，而且错误信息完全看不出是解析问题。.env.example 里已经是对的，别改。

第 3 步 · 冒烟检查（不花钱）

python -m scripts.smoke         # 检查配置与三个存储的连通性
python -m scripts.smoke --llm   # 额外真调一次模型（会产生少量费用）

验收：三个存储全绿。有红的先回第 1 步，不要往下走。

第 4 步 · 建表

python -m alembic upgrade head   # PostgreSQL 的表
python -m scripts.init_stores    # Milvus 的 collection（幂等，加 --drop 可重建）

两个库分工不同：PG 的表结构由 Alembic 管迁移；Milvus 没有迁移工具，schema 改了只能显式重建（--drop 会清空向量数据，要重新入库）。

第 5 步 · 下载年报

python -m scripts.fetch_reports                 # 默认样本
python -m scripts.fetch_reports 600519 000858   # 指定股票代码
python -m scripts.fetch_reports --years 2       # 每只取最近 2 份

从巨潮资讯网（证监会指定披露平台）下载官方原件，存到 data/raw/。

验收：data/raw/ 下有形如 600519_贵州茅台_xxx2025年年度报告.pdf 的文件。文件名格式是硬要求——公司代码、名称、年度全靠正则从文件名推断，格式不对会直接报错。

第 6 步 · 入库

python -m scripts.ingest                  # 入库 data/raw 下全部 PDF，约 ¥0.15/份
python -m scripts.ingest --pages 20       # 只处理前 20 页，省钱，先试这个
python -m scripts.ingest --exp exp01_baseline   # 指定实验配置（决定分块策略）
python -m scripts.ingest --force          # 内容没变也强制重建

这一步最慢，一份年报几分钟。第一次建议先用 --pages 20 跑通流程，确认无误再跑全量。

验收：日志里有「分块 xxx（策略=heading）：父块 N，子块 M」，且没有报错。

第 7 步 · 起服务

uvicorn app.main:app                           # 后端，8000
chainlit run frontend/app.py --port 8001       # 前端，另开一个终端
arq app.worker.Settings                        # Worker，只在用上传接口时需要

打开 http://127.0.0.1:8001。

第 8 步 · 验收：问五个问题

04四、系统全景

两条链路：离线把 PDF 变成可检索的块，在线把问题变成带引用的答案。

【离线 · 入库】  scripts/ingest.py
  PDF ──解析──> ParsedBlock ──切块──> ChunkUnit ──向量化──> ┬─> PostgreSQL（父块+子块全文）
       pdf_parser     chunker          indexer            └─> Milvus（只有子块+向量）

【在线 · 问答】  app/graph/build.py
  问题 → guard_in → analyze_query → cache_lookup ─┬─ chat  → 直接回答
                                                  ├─ agent → ReAct 循环（查+算）
                                                  └─ rag   → retrieve → grade → generate → verify
                                                                      ↓
                                                            cache_store → 答案 + 引用

两个库各存什么

PostgreSQL chunksMilvus fin_chunks
存谁父块 + 子块（全量）只有子块
正文content Text，无长度限制content VARCHAR(8192)，按字节算
向量无dense_vector(1024) + sparse_vector(BM25 自动生成)
过滤字段有索引但不用于检索doc_key company_code report_year period chunk_type statement_type strategy
随块带出—unit heading_path page_start parent_uid
主要用途父块还原、审计、重建 Milvus混合检索

PG 一共 7 张表：documents（文档元信息与入库状态）、chunks（块）、financial_metrics（结构化指标，尚未启用）、评估四件套 eval_datasets / eval_items / eval_runs / eval_results。定义全在 app/store/models.py。

05五、入库链路详解

入口 scripts/ingest.py，主逻辑 app/rag/indexer.py:174 ingest_pdf。五个阶段。

  1. 从文件名推断元信息

    正则 ^(\d{6})_([^_]+)_.*?(\d{4})\s*年 取出股票代码、公司名、年度，拼成 doc_key（如 600519_2025_annual）。推断失败直接报错而不是猜默认值——错的 doc_key 会污染整个检索过滤。

    indexer.py:69 infer_meta

  2. 解析 PDF → ParsedBlock 列表

    逐页：① page.find_tables() 找表；找不到但页面"看起来有表"就回退到文本对齐策略（中国平安 370 页只有 6 页能检出表，因为它的表没画框线）② 单元格粘连就按词坐标重建 ③ 正文段和表格按页面纵坐标混合排序（不这样做，表格会拿到整页最后一个标题，出现标题内容错配）④ HeadingTracker 维护标题路径 ⑤ render_table 渲染成带量纲声明的 Markdown。

    pdf_parser.py:727 parse_pdf → ParsedDocument(blocks)

  3. 切块：先聚父块，再切子块

    group_parents 把连续的同标题正文合并成父块（上限 3000 字），表格永远自成一块（和正文混在一起，切分时容易把表头和数据分开）。然后每个父块切子块：正文走 RecursiveCharacterTextSplitter（512 字 / 重叠 64，按段落→句子→词回退），表格走 split_table 按行切、每一片都重新带上表头和量纲——否则切出来的片段里数字没有列名也没有单位，等于废片。

    chunker.py:222 chunk_document → list[ChunkUnit]

  4. 向量化：只给子块算

    父块不进向量库（也进不去，实测最大 10636 字节超过 Milvus 的 8192 上限），命中子块后按 parent_uid 从 PG 取回即可。模型 text-embedding-v4，1024 维，百炼的批量上限是 10 条。

    indexer.py:92 embed_texts

  5. 双写：先 PG 后 Milvus

    顺序不能反——先写 Milvus 失败的话会留下无法回溯的孤立向量，而先写 PG 可以用它做补偿重建。幂等靠文件的 content_hash，同一文件重复入库不重复花 embedding 的钱。

    indexer.py:132 _save_chunks_pg → indexer.py:159 _write_milvus
这里有个经典的坑

Milvus 的 VARCHAR(n) 中 n 是字节不是字符。unit 字段原来开 8 字节，而「百万元」三个汉字是 9 字节——招商银行入库直接失败，报 length of varchar field unit exceeds max length。这个坑在项目里栽过两次（第一次是父块超 8192）。中文字段一律按字节留余量。

06六、一个块长什么样

这是理解整个项目最快的一步。看清楚存进去的到底是什么文本，后面检索和生成的设计就都讲得通了。

一个表格子块的 content 实际长这样（由 pdf_parser.py:678 render_table 生成）：

【单位：千元　币种：人民币】        ← 量纲，第一行
合并资产负债表                      ← 口径，跨页继承来的
六、主要会计数据和财务指标           ← caption / 标题
| 项目 | 2025年 | 2024年 | 2023年 |
| --- | --- | --- | --- |
| 营业收入 | 43,945,411 | 38,537,237 | 33,719,935 |
| 经营活动产生的现金流量净额 | 53,345,930 | 60,511,572 | 57,902,611 |
【按年份】营业收入：2025年=43,945,411；2024年=38,537,237；2023年=33,719,935

三个设计全在这段文本里：

  • 第一行的量纲——不写在正文里，模型看不到（它读不到数据库字段），数值就会读错 1000 倍。
  • 第二行的口径——合并与母公司两张表在原 PDF 里逐字相同，因为报表标题只印在起始页，而表横跨两三页。不把标题继承下来，这两种块在文本上完全无法区分。
  • 最后的「【按年份】」行——三年并列表里"第几列是哪一年"要靠模型数列，很容易错；干脆在解析时展开成显式的键值对。

对应的数据结构 ChunkUnit 在 chunker.py:37，字段和 PG 的 chunks 表、Milvus 的 fin_chunks 一一对应。chunk_uid 由 sha1(doc_key|strategy|level|seq) 生成——同一份文档重新解析必须得到相同 ID，否则增量更新无从比对。

07七、问答链路详解

整个流程是一张 LangGraph 状态图，装配全在 app/graph/build.py 的 148 行里。状态结构在 state.py。

三条分支怎么分的

判断标准不是"涉及几家公司"，而是"最终那个数字能不能从一页表格里直接抄下来"：

分支什么时候走典型问题
chat不需要查资料「你能做什么」
rag答案能从某一页直接读到「2025年营业收入是多少」
agent答案必须算出来，或要多轮检索「四个季度合计」「同比增长多少」「哪家更高」

置信度不足时兜底走 agent 而不是 rag——agent 是 rag 的能力超集，判错只多花钱；反向判错会直接答错。

检索那一步具体在做什么

这是整个系统的核心，全部在 app/rag/retrievers.py：

  1. 拼标量过滤表达式

    把抽出来的公司代码、年份、报表类型拼成 Milvus 的 filter 串，下推到检索层而不是检索完再过滤。因为 BM25 对年份完全无感（2023 与 2024 两条得分相同），公司和年份只能靠标量过滤卡住。strategy 也必须参与——不同实验的块共存于同一集合，不隔离就会互相污染，消融对比直接失效。

    retrievers.py:131 build_expr

  2. 年份要先扩展

    report_year 是文档的年度，用户问的是数据的年度。一份 2025 年报含 2023–2025 三年数据，用 report_year == 2024 过滤会直接返回空集。所以查 2024 的数据要扩成 [2024, 2025, 2026]。这个缺陷曾导致 61 题中约四分之一被误判为「检索无结果」而拒答，而且因为在检索阶段就空了，调相关度阈值完全无效——排查时极易被误导。

    retrievers.py:112 expand_report_years

  3. 混合检索，RRF 融合

    向量路（dense，top 20）和 BM25 路（sparse，top 20）各查一次，两路都带同一个过滤表达式，用 RRFRanker(60) 融合。配置可切成纯 dense 或纯 sparse，用于消融。

    retrievers.py:214 retrieve → client.hybrid_search

  4. 点名召回「近三年主要会计数据」表

    这张表是年报里唯一把多年数据并列、每列明写年份的表，但每个科目只出现一次，在词频检索里天生吃亏——实测它在朴素查询下一次都没进过前 20。解析阶段已经把它标成 chunk_type=table_summary，这里直接按标签取，不跟词频赛跑。（早期做法是往查询里拼表名，但上交所叫「近三年主要会计数据和财务指标」、深交所叫「主要会计数据和财务指标」，写死一种只覆盖一半公司。）

    retrievers.py:178 force_summary_table

  5. 重排 —— 默认关闭，因为实测有害

    关闭时按原序截断到 top_n，这样开关重排只改变排序、不改变块数，消融才是在比排序质量本身。实测开启后掉 6.1 点，两组置信区间不重叠，成本还高 5%。机制很清楚：gte-rerank-v2 是通用语义模型，「母公司资产负债表」与「合并资产负债表」在语义上几乎无法区分，它没有「合并是财务数据默认口径」这个领域常识，于是把 RRF 本来排对的顺序打乱了——口径辨析类从 100% 掉到 81.2%。

    retrievers.py:277 rerank

  6. 父块还原（small-to-big）

    拿命中子块的 parent_uid 去 PG 查父块，用父块替换子块送进上下文——检索靠子块精准，生成靠父块完整。按 parent_uid 去重（多个子块常同属一个父块，重复进上下文只增加成本不增加信息），受字符预算约束，表格父块不中途截断。

    retrievers.py:313 expand_parents → PG chunks 表

  7. 编号后进 prompt

    每块编上 [1] [2] …，连同页码格式化进上下文。生成时强制模型用这些编号标引用，verify 节点再核验编号没越界。

    rag.py:83 _format_context → rag.py:92 build_citations
最值钱的一个参数

第 5 步的 top_n（送进上下文的块数）从 5 放宽到 15，正确率 +14.9 点，页码召回从 67.4% 升到 86.8%。信息不是没检索到，是检索到之后被截断扔掉了——检索 top20 召回 95.9%，截断到 top5 只剩 44.9%。这是整个项目里最有效的单个改动，而它很少被教程讨论。

两级缓存：一个反直觉的发现

精确缓存（Redis）管「同一个问题原样再问」，语义缓存（Milvus）管「问法不同但问的是同一件事」。语义缓存在财报场景有特有风险：问法只差一个实体时向量相似度仍然很高，纯按相似度匹配会返回一个精确但错误的数字。实测（茅台的四种问法，阈值 0.97）：

只差什么余弦相似度离 0.97 阈值还有
公司（宁德时代 vs 贵州茅台）0.58240.39
年份（2025 vs 2024）0.86–0.870.10
科目（营业收入 vs 净利润）0.92240.05 ← 最危险

最危险的是科目而不是年份，这与设计时的直觉相反。所以 entity_key 必须同时约束（公司, 年份, 科目）三者，精确相等才允许命中，向量相似度只用来吸收问法差异。cache.py 顶部有完整记录。

Agent 的三道护栏

护栏阈值设计要点
步数上限8调用前检查——超限还调一次是白花钱
工具连续失败3失败原因回传给模型，让它换参数而不是直接中断
成本预算¥0.15单次问答的硬上限

触顶时强制收敛作答，而不是报错——用户宁可拿到「基于已查到的部分，结论是…」，也不要一句「超出步数限制」。

两个工具：retrieve_report（查年报）和 calculate（算数）。calculate 用的是基于 AST 白名单的受限求值，不是 eval——把表达式交给 eval 等于把任意代码执行权交给模型输出。只放行数值、四则运算和 abs/round/min/max/sqrt，拒绝名称、属性、下标、推导式、lambda，并对指数设上限（9**9**9 能用极小的输入耗尽内存）。

一个坑过人的机制

exp_id 跟着请求在 GraphState 里流转，并且同时出现在三个地方——Milvus 的 strategy 标量字段（隔离不同分块策略的块）、缓存键前缀（上组实验的缓存不污染这组）、评估记录。

节点内必须用 experiment_of(state) 取配置，直接调用无参的 load_experiment() 会去读环境变量 EXP_ID，命令行 --exp 就形同虚设。这个 bug 曾让三组消融实验跑的全是同一套配置，指标自然毫无差异，而且完全不报错。见 state.py 顶部注释。

所以"换一组参数跑实验"的正确做法是：复制一个 configs/experiments/expNN_xxx.yaml → 改里面的值 → python -m eval.run --exp expNN_xxx。不改代码。

09九、评估体系

这是项目里最值钱的部分，也是你做任何改动之后验证它是好是坏的唯一方式。没有评估，所有优化都是盲调。

怎么跑

python -m eval.run --dataset v2                      # 用当前实验配置跑
python -m eval.run --dataset v2 --exp exp04_wider    # 指定实验
python -m eval.run --dataset v2 --limit 5            # 小样本试跑

题目长什么样

{"question": "美的集团2025年归属于上市公司股东的净利润是多少？",
 "category": "table",                    ← fact|table|multihop|scope|refuse 五类
 "ground_truth": "43,945,411千元",
 "numeric_value": 43945411.0, "unit": "千元",
 "expected_doc_keys": ["000333_2025_annual"],
 "expected_pages": [9],                  ← 用来算页码召回
 "source": "auto_extracted", "verified": true,
 "note": "第二节 … 第9页，列头年份 2025；原文行：| 归属于…净利润（千元） | 43,945,411 | …"}

五类题里，scope（口径辨析）是这个项目特有的——同一科目分别问合并与母公司，成对出题，让「蒙对一个」拿不到分。

怎么判对错（eval/metrics.py）

  • 不用模型评判。数值题走 numeric_match：从答案里抽所有金额，按单位归一到「元」，容差 ±0.5% 比对。所以「16,883,810.25 万元」和「168,838,102,514.79 元」判为同一答案。好处是没有评判噪声、成本近似为零、对外无需解释。
  • 单位单独判（unit_declared）——答对数字却没说单位，在财报场景等于没回答。
  • 检索指标分两级：doc_recall（找对文档没有）和 page_recall（找对页没有）。两者差距大时说明"文档对了但不是那一页"——项目里出现过 93.9% 对 38.8% 的落差。
  • 所有指标报 bootstrap 95% 置信区间（默认 1000 轮）。intervals_overlap 返回 true 时不得声称有提升，只能记「无显著差异」。
  • 按类别分层报告——总体指标会被类别差异稀释，必须看分项。

结果落在哪

两处：PG 的 eval_runs / eval_results 表（带完整配置快照和 git sha，所以任何一次结果都可追溯到当时的代码和参数），以及 eval/reports/run_NNNN_expXX.md 的逐题明细。

目前已经跑了 60+ 次，报告都在那个目录里——这是一份现成的实验史，值得翻一翻。docs/benchmarks.md 是它的导读。

一条纪律

评估集一旦变更，历史指标全部作废，必须重跑。所以顺序只能是「先定评估集 → 再跑对照与优化」，反过来会白跑。

10十、常见操作手册

七个最常见的改动，每个都是完整步骤。点开看。

加一家公司的年报最常做
  1. 下载：python -m scripts.fetch_reports 600036（或手动放进 data/raw/，文件名必须是 代码_公司名_...YYYY年...pdf）
  2. 入库：python -m scripts.ingest（已入库的会按 content_hash 跳过，不重复花钱）
  3. 验证：问一个这家公司的问题，看能不能答上来
  4. 如果答不上来，先查这家公司的表有没有被抽出来：python -m scripts.probe_pdf --dump-page 9 看那一页的解析结果

注意：新公司不需要改任何代码或配置——可用语料是从 PG 的 documents 表动态读的（query.py:102 available_corpus）。

做一次消融实验核心工作流
  1. 复制一份基准配置：cp configs/experiments/exp00_debug.yaml configs/experiments/exp07_myidea.yaml
  2. 改 exp_id 为 exp07_myidea，只改你要测的那一个参数，其余保持完全一致
  3. 在文件顶部的注释里写清楚：这次改了什么、预期是什么、和哪一组对比
  4. 如果改的是 chunking 段 → 必须重新入库：python -m scripts.ingest --exp exp07_myidea（不同 strategy 的块按字段隔离，可以共存）
  5. 跑：python -m eval.run --dataset v2 --exp exp07_myidea
  6. 读 eval/reports/ 下最新的那份报告，看置信区间有没有重叠——重叠就是「无显著差异」，不能说有提升

常见错误：一次改两个参数。那样无论结果如何都无法归因，这次实验等于白跑。

改提示词见效最快
  1. 路由与实体抽取 → app/graph/nodes/query.py:61 的 _SYSTEM
  2. 最终答案生成（引用、单位的强制约束）→ app/graph/nodes/rag.py 的 _SYSTEM
  3. Agent 的工作方式 → app/graph/nodes/agent.py:47 的 _SYSTEM
  4. 改完一定要跑评估，提示词改动最容易"修好一个、弄坏三个"

这里是过拟合最高发的地方。项目里有过教训：对着 61 道题调了六轮提示词拿到满分，换到 182 题只剩 74.7%。往提示词里加的规则往往只对你看过的那几道题成立。能用结构性修复解决的，不要加提示词规则。

给 Agent 加一个工具中等
  1. 在 app/graph/tools.py:133 build_tools 里用 @tool 装饰器加一个函数
  2. docstring 就是给模型看的工具说明，写清楚什么时候该用、参数是什么意思——这比函数实现更影响效果
  3. 返回值要控制长度（现有的 MAX_SNIPPET = 1200），否则工具结果会撑爆上下文
  4. 失败时返回可读的错误信息而不是抛异常——护栏会把错误回传给模型让它换参数重试
  5. 在 agent.py 的 _SYSTEM 里补一句什么时候用这个工具
  6. 加测试：tests/test_m5_agent.py 里有现成的模式
加一个 Milvus 过滤字段三处都要改
  1. app/store/milvus_schema.py 的 _build_chunks_schema 加字段（VARCHAR 长度按字节算，中文留三倍余量）
  2. app/rag/indexer.py 写入处补上这个字段的值
  3. app/rag/retrievers.py 的 OUTPUT_FIELDS 和 build_expr 加上
  4. 如果这个字段要从 PDF 里抽，还要改 pdf_parser.py 和 chunker.py 的 ChunkUnit
  5. 重建 collection 并重新入库：python -m scripts.init_stores --drop 然后 python -m scripts.ingest --force

Milvus 没有迁移工具，schema 改了只能重建——这也是为什么加字段要谨慎。

加评估题最该做的事
  1. 往 eval/datasets/vN.jsonl 追加一行，字段格式见第九节
  2. expected_pages 一定要填，否则页码召回算不出来
  3. note 里抄上原文那一行——以后复查时不用再翻 PDF
  4. 导入并跑：python -m eval.run --load eval/datasets/vN.jsonl --dataset vN

批量造题可以用 python -m scripts.extract_key_metrics 先抽底稿，再 python -m scripts.build_eval_v2 --sample 20 抽样人工核对。自动生成的题必须抽检——现有 182 题里 124 题是自动生成的，只抽检了 16%。

换模型或加一家厂商最简单
  1. 加厂商：在 configs/models.yaml 的 providers 下加一行（base_url + api_key_env），不写任何代码——所有厂商都兼容 OpenAI 接口，这一层只是配置表 + 工厂函数
  2. 加模型：在 profiles 下加一个 profile，单价一定要填对，成本核算直接读它
  3. 在 .env 里配上对应的 API Key 环境变量
  4. 在实验配置的 generation.profile 里引用它

换生成模型会让历史指标全部不可比，消融对比必须固定生成模型。项目里实测 qwen-plus 对 qwen-flash 是 99.5% vs 98.4%，区间大幅重叠而成本差 4.3 倍——所以原计划的「按复杂度路由到不同模型」被数据否决掉了。

脚本输出重定向到文件后只剩半行，但退出码是 0 Windows 下 stdout 退回 GBK 代码页，打印「¥」「—」就抛 UnicodeEncodeError 进程当场死，而 ; echo $? 又把退出码洗成了 0 已在 scripts/__init__.py 强制 stdout 为 UTF-8。写新脚本记得走 python -m scripts.xxx
入库报 length of varchar field ... exceeds max length Milvus 的 VARCHAR 按字节算，中文一字三字节 改 milvus_schema.py 的长度常量，--drop 重建 collection 后重新入库
三组消融实验跑出来指标完全一样 节点里直接调了无参的 load_experiment()，读的是环境变量，命令行 --exp 没生效 所有节点必须用 experiment_of(state)。这个 bug 不报错，极难发现
某类问题全部拒答，调相关度阈值完全无效 检索阶段就返回了空集，阈值根本没被触及。多半是 report_year 过滤——它是文档年度不是数据年度 确认走了 expand_report_years。把 LOG_LEVEL=DEBUG 打开看实际的 filter 表达式
检索结果里混进了别的实验的块 build_expr 没带 strategy 过滤 所有检索路径都必须带，包括 force_summary_table
某家公司一道题都答不出来 它的表格没被抽出来。常见于无边框表（中国平安）、年份行排在表格框外（招行、中石油） python -m scripts.probe_pdf --dump-page N 看那一页。这是 open-issues.md 的 P1-5，至今未解决
Agent 说「调用 calculate 工具进行计算。」然后就结束了 模型宣告要调用但实际没发出 tool_call 已有检测（agent.py 的 MALFORMED_CALL）：给用户看的最终回答里永远不该出现内部工具名
Langfuse 没数据 没配 Key 时是静默跳过，不是错误 注册账号填 LANGFUSE_PUBLIC_KEY / SECRET_KEY。这是 open-issues 的 P2-3
服务起来了但答不了问题 某个存储没连上，但启动时故意不崩溃 先看 GET /readyz，它会告诉你哪个挂了
改了配置没生效 load_experiment 有 lru_cache 重启进程

docs/lessons.md 里有完整的 28 条，包括每条是怎么定位到的——定位过程比结论更值得看。

12十二、已知边界

接手的人必须知道这些。完整清单在 docs/open-issues.md，每条都带「下一步动作」和「为什么还没做」。

级别问题下一步
P0-1v2/v3/v4 评估集都已消耗，后续修复的真实收益无数据用全新语料建 v5 留出集，一次性评估。最该做的一件
P1-5中国平安、中国石油仍抽不出指标，两家公司零覆盖逐页对比 find_tables 与坐标重建，定位卡点
P1-6「重述前/重述后」「调整前/调整后」拆列表的年份归属错解析阶段把子列头并进表头
P1-4financial_metrics 表建了但结构化抽取未实现，SQL 路径未开放抽 50 条人工核对，达 95% 才开放
P0-3同配置多轮跑，正确率在 97.3%–100% 间浮动（1–2 道题）多轮取多数，或固定检索侧随机性
P2-2增量更新简化为全量重建按块级 hash 做差分

能力边界（不是 bug，是设计范围）

  • 只支持文本层可提取的 PDF，不做 OCR 扫描件
  • 单机规模：17 家公司约 1.3 万个块，没做过大规模压测
  • 评估覆盖 < 语料覆盖：语料 17 家，评估集只覆盖其中一部分
  • 182 题中 124 题为自动生成，分层抽检 20/20 正确，但只覆盖 16%
怎么看待 README 里的 100%

那是开发集上的数字。同一套代码在留出集上是 83.7%。项目里记录过两次"测出自己的水分"：第一次在 61 题上调六轮满分，换到 182 题只剩 74.7%（落差 22.6 点）；第二次吸取教训后差距缩到 3.3 点。正确的说法是「在这些题上不再有失败案例」，不是「系统准确率 100%」。

13十三、七天学习路径

自底向上：数据怎么进去 → 怎么存 → 怎么取出来 → 怎么编排 → 怎么验证。每层学透再上一层，每天都有动手动作。

第 0 步（半天）：按第三节把环境跑起来。只做两件事——确认五个容器 healthy，确认 python -m scripts.ingest --pages 20 能跑完一份 PDF。先不要问问题、不要看前端，在线链路留到第 7 天。

天层读什么动手做什么
D1 入库主流程
先看骨架		 scripts/ingest.py → indexer.py:174 ingest_pdf 通读 ingest_pdf，把五个阶段抄在纸上，写清楚每个阶段的输入输出类型。暂时不要跳进任何一个阶段内部。
D2 解析层·产物 pdf_parser.py 的 ParsedBlock（85 行）、render_table（678 行） 写十行脚本调 parse_pdf()，打印前 30 个 block 的 kind / heading_path / unit / statement_type / text[:200]。先看见真实产物，再看它怎么产生的——这是读这个文件唯一不崩的顺序。
D3 解析层·实现
最难的一天		 pdf_parser.py:727 parse_pdf 主循环，配 tests/test_m1_parser.py 按顺序拆：① 正则常量 ② HeadingTracker ③ find_tables + 坐标重建兜底 ④ 正文与表格按 y 坐标混排 ⑤ 跨页的三个继承（单位、口径、表格）。每读完一块去测试里找对应用例跑一遍。
D4 分块层 chunker.py（277 行，全项目最好读的文件之一） 对同一份 PDF 调 chunk_document()，统计父子块数量，挑三个子块打印全文。然后把 table_atomic 关掉再跑一次，对比表格被切成了什么样——你的第一次破坏实验。
D5 存储层 milvus_schema.py + models.py + 回看 indexer 的双写 直接查库：PG 里 select * from chunks limit 5，Milvus 用 scripts/probe_milvus.py 捞几条。亲眼确认父块只在 PG、子块两边都有。回答一个问题：为什么 unit 字段要开 32 字节？
D6 检索层 retrievers.py（360）+ experiment.py（134） 照第七节的七步走一遍。动手：手工构造 QueryFilters 直接调 retrieve()，打印命中的 uid 和分数。再把 mode 改成 dense / sparse 各跑一次，对比差在哪。
D7 编排层 + 验证 build.py → state.py → nodes/rag.py → nodes/query.py → nodes/agent.py 这时才起服务问第三节那五个问题，去日志里确认过滤表达式、命中的块、父块还原后的上下文。然后跑第一次完整评估，再做第一次正式实验（把 top_n 从 15 改回 5，看掉多少分）。
为什么是这个顺序

自底向上的代价是前四天看不到完整效果，很容易忍不住跳去看前端。别跳。坚持到 D7 的收益是——你看在线链路时，检索返回的每个块从哪来、为什么长那样，你全都知道。反过来从图开始看，检索对你就是个黑盒，只能记住"它调了个 retrieve"。

一句话总结这个项目的设计信条

「参数进配置，结构进代码，结论靠数据。」凡是要做对比实验的东西都在 YAML 里；凡是确定性的结构处理都写死在解析阶段；凡是声称有提升的都要有置信区间。读代码时拿这三条当线索，大部分设计选择都解释得通。
